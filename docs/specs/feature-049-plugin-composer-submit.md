# Feature-049：插件在用户点击后提交聊天消息

**日期：** 2026-11-09
**状态：** 草案，待确认（2026-11-09 起草；同日按评审意见简化：去掉点击凭证、合并状态码、取消独立冷却、并入引用授权。只读代码与播放器讨论得出，未实现、未运行）
**范围：** 宿主清单与安装确认、插件视图到聊天的提交入口、输入框发送路径。首个预计调用方是 `plugins/transcript-player/`（XTLaw 播放器），但其智能纪要的保存和写回不在本规格内。
**承接：** [Feature-013 工作台选区引用](feature-013-workbench-selection-reference.md)、[Feature-033 文档插件契约](feature-033-document-plugin-contract.md)、[Feature-048 文字稿播放插件](feature-048-transcript-player-plugin.md)
**不要和这些混用：** [Feature-047 聊天内容触发插件动作](feature-047-plugin-chat-actions.md) 是聊天里的链接去调用插件。本规格方向相反：插件视图里的一次点击，向聊天提交一条用户看得见的消息。

## 文件与术语说明

| 原名称 | 中文含义 | 用途 |
| --- | --- | --- |
| `composerSubmit` | 提交聊天消息权限 | 安装时单独授权；没有它不能提交，也包含附带引用 |
| `contributes.composerSubmits` | 可提交消息声明 | 冻结标题和正文，插件运行时不能改写指令 |
| `context.composer.listTargets` | 列出可接收的聊天 | 只返回当前能接收引用的目标 |
| `context.composer.submit` | 提交一条消息 | 视图在用户点击后调用 |
| `useChatComposer.ts` 的 `submit()` | 现有发送函数 | 只发送输入框里的当前草稿 |
| `composer.captureQuote` / `composer.addQuote` | 现有引用接口 | 只把材料放进草稿，不发送 |
| `agent.actions` | 任务动作 | 旁边独立执行，不向主对话发消息 |
| `models.generateText` | 插件自己的模型调用 | 没有当前对话和工具，不是本规格要叫醒的 Agent |

## 1. 背景

播放器右侧的「智能纪要」要由当前聊天里的 Agent 来写，再交回播放器。播放器自己不能改聊天，也不能假装点了发送按钮。

现在只有两条近路，都不够：

- 引用和 `insertText` 只进草稿。`composer.actions` 的说明写明返回 `{insertText}` 也不会发送。用户还得再点一次发送。
- `agent.actions` 由任务事件或任务菜单触发。它不插入用户消息，也不占用主对话的工具。即便声明 `permissions.models`，也只是插件自己的一次无工具文本调用，不是正在对话的那个 Agent。

所以要在宿主增加一种更窄的能力：用户在插件里点一下，宿主向用户选定的聊天提交一条事先声明好的消息。消息在聊天里看得见，随后仍走普通对话。Agent 写不写、怎么写回插件，由它自己的工具决定，不在本规格里强制。

## 2. 已定

这些来自 2026-11-09 的讨论，实现时不要改回旧方案。

1. **不复用 `agent.actions`。** 那是插件旁路执行，不是代发用户消息。
2. **不模拟点击发送按钮。** 焦点和草稿一变就会发错。
3. **后台不能发。** 任务创建、输入提交、回复完成、定时命令和 Agent 工具都不能调用本能力。
4. **一次点击之后，仍由当前聊天里的 Agent 处理。** 不改成插件内部的 `models.generateText`。
5. **提交结果必须是一条看得见的用户消息。** 用户可以阅读，也可以停止这一轮。
6. **有多个聊天时不能猜。** 必须由用户选定。
7. **不动用户正在写的草稿。** 不插入、不清空、不把草稿一起发出去。

## 3. 目标与非目标

**目标**

- 插件在清单里声明一条或多条固定消息。
- 用户点击插件自己的按钮后，视图把该声明提交到用户选定的聊天。
- 可以附上这次点击已经取得的引用，例如一段文字稿。引用规则沿用现有授权，不扩大读取范围。
- 没有可接收的聊天、目标失效、正在发送、引用超限或声明对不上时，明确失败，不发出半条消息。

**非目标**

- 不实现播放器的智能纪要存储、广播和「写入纪要」工具。那是播放器插件的后续规格。
- 不让插件自拟提示词、系统提示、模型或隐藏指令。
- 不把消息插进队列。目标正在回复或已有等待中的输入时，直接拒绝。
- 不改 Feature-047 的聊天链接，也不改现有引用卡片和「定位来源」。
- 不新增 `apiVersion`。用 `engines.lexora` 的下限标记第一个提供本能力的应用版本。当前 `0.5.4` 不包含本能力，不能声明兼容。

## 4. 方案

### 4.1 清单

新增权限 `permissions.composerSubmit`，默认 `false`。它允许提交本插件已声明的消息，并允许随消息附带引用快照；不包含读文件、写草稿或调用模型。附带引用不再另要 `references` 或 `composerReference`，但引用仍走现有快照校验（形状、限额、文件版本），不扩大读取范围。

新增贡献 `contributes.composerSubmits`，最多 8 条（首个调用方只需 1 条）。`id` 唯一性、长度等校验沿用现有 `contributes` 的通用校验，不另写一套：

```json
{
  "permissions": { "composerSubmit": true },
  "contributes": {
    "composerSubmits": [{
      "id": "<plugin-id>.write-summary",
      "title": "写智能纪要",
      "text": "请根据引用的文字记录写智能纪要，并写回播放器。"
    }]
  }
}
```

- `id` 以插件 ID 加 `.` 开头，且在本插件内不重复。
- `title` 是 1–40 个字符，只用于安装确认页，不显示在聊天里。
- `text` 是 1–500 个字符的固定正文。运行时不能替换、拼接或追加。
- 不提供 `when`、参数模板或模型字段。需要不同说法时，声明另一条，而不是在运行时改字。

升级时，`addedExtensionPermissions` 把新增的 `composerSubmit` 标为新权限。安装确认页用宿主写死的说明，不用插件自己的营销句：

> 可在你点击后，向选定的聊天提交一条预先写明的消息，并可附带引用材料。消息会显示在聊天中，并可能开始一次 Agent 回复。

确认页同时列出每条声明的 `title` 和完整 `text`。用户看不到正文，就不能确认这项权限。

### 4.2 谁可以调用

只有交互视图可以调用。视图须位于前台窗口、当前可见，并且调用时持有焦点。以下入口一律没有这个方法：

- 插件宿主入口 `activate`
- `agent.tools` 与 `agent.actions`
- 定时命令、通知和后台命令
- 装饰、内容插槽、替换控件、窗口遮罩

扩展桥是异步消息，宿主不能可靠地看到浏览器内部的用户激活标记，也就无法证明某次调用来自真实点击。这里不引入点击凭证：脚本本来就能在任何时刻申请凭证，它拦不住已聚焦视图里的脚本，只会增加状态和测试。宿主只校验「前台可见且持有焦点」。已聚焦的视图仍可能由脚本调用；固定正文、安装时展示正文、目标忙则拒绝和可见消息用来限制后果。

### 4.3 选择聊天

`context.composer.listTargets()` 返回 `{ targets: [{ id, label }], defaultId }`。目标集合与现有引用捕获相同：当前能接收引用的聊天。它不返回任务正文、草稿内容或历史。

- 没有目标：插件提示先打开聊天输入框，不提交。
- 只有一个目标：可以直接用它。
- 有多个目标：插件必须让用户选择。禁止用 `defaultId` 静默选中，也禁止选择「当前焦点」以外的猜测规则。`defaultId` 仍只表示引用菜单的预选项。

目标 ID 是不透明字符串。插件不能传入任务 ID、分支 ID 或自己保存的旧 ID。

### 4.4 提交

```ts
const result = await context.composer.submit({
  id: `${context.extension.id}.write-summary`,
  targetId,
  quotes,
})
```

`quotes` 可选，最多 4 条。每条使用现有引用快照的形状和限额，包括 `BUDDY_QUOTE_TEXT_LIMIT`（引用正文上限）以及播放器已经遵守的选区上限。超限、快照校验失败、文件版本已变化，整次提交失败，不截断、不改成纯文本发送。没有引用也可以提交；播放器若要求必须有文字稿，由播放器自己在调用前检查。

返回三类状态，用 `reason` 区分具体原因：

| `status` | `reason` | 插件应显示 |
| --- | --- | --- |
| `submitted` | —（附带 `messageId`） | 可提示已发送到哪个聊天 |
| `retry` | `busy`：目标正在回复，或已有等待中的输入、本插件已有一次提交在进行 | 请等这一轮结束后再试 |
| `retry` | `no-target`：没有目标、目标已关闭 | 请打开或重新选择聊天 |
| `retry` | `not-visible`：视图不再可见或没有焦点 | 请回到该视图再点一次 |
| `rejected` | `too-long`：引用超限或快照校验失败 | 说明材料太长，需缩短或拆分 |
| `rejected` | `not-allowed`：未授权、声明不存在或调用方不允许 | 提示需要更新授权或升级宿主 |

插件按 `status` 分三路处理即可，`reason` 只用来选提示文案。

旧宿主没有该方法时，插件先检查 `typeof context.composer.submit === 'function'`，并提示升级。

频率：不设独立冷却。同一插件同时最多 1 次提交在进行；提交成功后目标进入「正在回复」，下一次点击会因 `busy` 被拒，这本身就是自然限流。出现滥用再考虑加冷却，本期不做。

### 4.5 宿主如何发送

提交不经过 `useChatComposer.ts` 的 `submit()`，因此不会执行草稿里的 Slash 命令、本地输入命令，也不会读走用户正在写的字。

宿主构造一条新的用户消息：

1. 聊天里只出现**一个**普通用户气泡，正文就是声明里的 `text`，与用户手打、点发送的效果一致。不加来源标签，不加宿主前缀，模型看到的也是同一段正文。
2. 引用以普通聊天引用附在这个气泡上，沿用现有快照、权限和「定位来源」。不把引用先放进草稿再发送，也不拆成第二条消息。
3. 目标沿用该聊天当前的 Actor 和模型选择。插件不能指定 Actor、模型、系统提示或工具。
4. 目标正在运行，或 `chat_queue` 里已有该分支等待中的输入时，返回 `busy`，不入队。
5. 成功后，这条消息和随后的 Agent 回复与手打消息使用同一条对话路径。用户可以停止。停止不会回滚已经显示的提交消息。

草稿保持原样，包括尚未发送的引用和半句话。

### 4.6 播放器怎么用（本规格只规定调用方式）

播放器侧的完整行为见 [Feature-050](feature-050-transcript-player-summary.md)。这里只固定调用方式：「让 Agent 写纪要」走本能力，不把整段提示塞进草稿。预期顺序是：

1. 没有字幕时，按钮不可用，仍显示现有空状态。
2. 点击后调用 `listTargets()`。多个聊天时弹出与现有引用相同的选择；只有一个时直接继续。
3. 把当前文字稿作为一条引用附上。文字稿超过引用上限时不提交，提示缩短或拆分，不截断。
4. 提交声明好的那一句。成功后聊天里出现一个用户气泡，Agent 按普通对话处理。
5. Agent 是否写回右侧纪要页，取决于后续的播放器工具。本规格不要求这次回复一定写回。

## 5. 兼容

- 不声明 `composerSubmit` 的插件看不到新方法，行为不变。
- 现有 `captureQuote`、`addQuote`、`insertText` 仍不发送。
- `agent.actions` 的触发清单不增加本能力。
- 附带引用只需 `composerSubmit`；插件若另有 `references` 或 `composerReference`，行为不变。
- 能力目录增加 `composer.submit`，说明它只存在于前台可见且聚焦的交互视图，并写明首次提供的应用版本。
- `plugin-creator` 增加一页说明：固定正文、目标选择、失败状态，以及为什么不能从动作或工具里提交。

## 6. 风险与边界

- **聚焦视图仍可能脚本提交。** 宿主看不见真实鼠标事件，点击凭证也防不住脚本，所以不做。固定正文、安装时展示正文和「目标忙则拒绝」用来避免任意提示词和连续消耗。
- **引用内容由插件提供。** 引用并入同一权限后，宿主只校验快照形状、限额和文件版本，不验证内容是否忠实。引用会随消息显示在聊天里，用户可见。
- **消息会花钱。** 这是用户点击加安装授权后的明确结果。每次提交前不再弹第二层确认，否则就回到「还要点一次」。
- **引用不是完整读权限。** 超限必须失败。播放器不能为了塞进引用而要求宿主读整份字幕文件。
- **气泡不标注来源。** 提交的消息和手打消息外观一致。这是有意的：正文在安装确认页已完整展示，用户点击前已知道会发出什么，也能随时停止这一轮。代价是事后从聊天记录里看不出这句是插件代发的；若以后需要追溯，再加标签，本期不做。
- **不要入队。** 排队会让一次点击在几分钟后突然开始，用户已经离开当时的上下文。

## 7. 验证计划

- 单测可在 WSL 跑：清单 schema、新权限差分、声明正文不能被参数替换、无目标或失效目标不发送、`busy` 时不写 `chat_queue`、超限不截断、不声明 `references` 也能附带引用、宿主入口与动作调用被拒绝。
- 类型检查覆盖新增的视图方法；旧视图代码不引用该方法时仍可通过。
- 桌面实测、Playwright 和打包在 WSL 做不了。回 Windows 本机验收，记录里写「未跑」。至少看三种情况：唯一聊天直接出现一个用户气泡；多个聊天必须选择；正在回复时点击不入队，草稿仍在。

## 8. 验收清单

- [ ] 未授予 `composerSubmit` 时，视图调用被拒绝
- [ ] 安装确认页展示宿主固定说明，以及每条声明的标题和完整正文
- [ ] 用户点击后，选定聊天出现一条新用户消息；草稿内容不变
- [ ] 聊天里只出现一个用户气泡，正文等于声明的 `text`，无来源标签和宿主前缀；引用附在同一气泡上
- [ ] 多个聊天时不自动选定；没有聊天时不提交
- [ ] 目标正在回复或已有等待输入时返回 `busy`，队列不新增
- [ ] 引用超限时整次失败，不发出不带引用的消息
- [ ] 宿主入口、任务动作、Agent 工具和定时命令无法提交
- [ ] 插件停用或更新后，旧视图不能继续提交
- [ ] 只声明 `composerSubmit`（不声明 `references`）也能附带引用，且引用仍走快照校验
- [ ] 不声明该权限的旧插件，引用和发送行为不变
