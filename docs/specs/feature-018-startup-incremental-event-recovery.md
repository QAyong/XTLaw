# Spec-018：启动历史事件按变化恢复与加载耗时优化

**日期：** 2026-10-04

**状态：** 首期已实现，定向测试与独立目录 Windows 打包验证通过；完整预检未全部通过，安装包真实启动性能尚未验收

**首期选择：** 稳定历史跳过；变化或不可信的运行记录完整重建

**文件说明：** 保留原文件名和编号；文件名中的 incremental 不代表首期实现事件尾部增量读取。

## 1. 背景与通俗说明

用户反馈：应用启动时加载动画持续十多秒。

当前启动方式相当于“每次开门营业，都把过去所有账本重新算一遍”。首期改为：

> 没变、且上次已经可靠算好的旧账，不再算；变过或有疑问的账，仍按现在的方法完整重算。

先做到“别重复干旧活”，不同时追求“只读取新增的几行”或“把恢复搬到后台”。

这里的“同步”仅指本机事件日志与数据库整理结果保持一致，不涉及联网、云端上传或跨设备同步。

- **运行记录**：一次任务执行的记录；一个会话可以包含多次执行。
- **事件日志**：记录执行过程中发生的事实，例如消息完成、工具调用、任务结束。
- **数据库投影**：将事件整理成便于界面查询的状态、消息、审批和用量数据。
- **检查点**：在数据库中记录“这一份日志已可靠整理”，用于判断下次能否跳过。
- **可信标记失效**：先撤销“已经整理好”的标记；不删除日志或对话。

目标是减少日常启动的重复读取与重建，保留异常恢复入口，不删除或缩短用户历史数据来换速度。轻量检查与完整校验的保证不同，具体边界见第 4.4 节。

## 2. 证据与事实边界

### 2.1 已观察并复核的本机耗时

本机 0.9.4 应用诊断日志中的记录如下；本次审查重新核对了原始日志，而非仅引用旧方案：

| 启动时间（日志 UTC 时间） | 应用就绪耗时 | 历史事件重放耗时 | 占比 | 原始记录 |
|---|---:|---:|---:|---|
| 2026-10-03 13:39 | 10,804 毫秒 | 8,733 毫秒 | 约 81% | `application.3.jsonl`（诊断日志）第 52、371 行 |
| 2026-10-03 14:53 | 8,263 毫秒 | 6,439 毫秒 | 约 78% | `application.2.jsonl`（诊断日志）第 52、375 行 |

第二次记录中，窗口在启动计时约 911 毫秒时就绪，前端恢复阶段约 334 毫秒。因此，这些样本的主要瓶颈是历史事件重放，不是窗口创建或动画绘制。诊断日志会轮转，文件名及行号仅用于说明本次复核来源。

**不能据此下结论的事项：**

- 未进行全新空数据安装测试，不能将已有历史数据的耗时解释为首次安装耗时。
- 未独立测量重放内部各环节，尚不能断定文件读取、事件校验和数据库重建分别占多少。
- 两条样本不是性能分布，也不是优化后的性能承诺。
- 安装包日志与当前仓库未确认是完全相同构建；实施前必须在目标构建重新建立基线。

### 2.2 实施前已确认的代码路径与限制

下表记录优化前的行为与设计约束；实施后的入口、检查点和验证结果见第 10 节。

| 文件与标识 | 实施前行为及对方案的约束 |
|---|---|
| `apps/buddy/service/src/index.ts`（本地服务入口） | 等待 `runtime.event_replay`（历史恢复启动阶段）中的 `eventLog.replayAll()`（全量重放函数）完成，之后初始化服务并宣布就绪 |
| `apps/buddy/service/src/events/RunEventLog.ts`（事件日志协调器） | `replayAll()` 逐个串行调用 `replay()`（单个运行记录恢复函数），读取、修复日志并重建投影；恢复还初始化 `#nextSequences`（内存中的下一事件序号） |
| `apps/buddy/service/src/events/RunEventStore.ts`（日志文件存储器） | `readAndRepair()`（读取修复函数）全文读取；`listPersistedRunIds()`（持久化记录筛选函数）仅筛选传入的数据库运行编号，日志目录定位也依赖数据库中的会话映射 |
| `apps/buddy/service/src/events/RunEventQueries.ts`（事件查询器） | 从数据库 `runs`（运行记录表）枚举运行编号并查询所属会话，不是独立日志目录发现机制 |
| `apps/buddy/service/src/events/RunEventProjector.ts`（数据库投影器） | `project()`（正常追加投影函数）与 `rebuild()`（完整重建函数）已有内部事务；重复执行 `project()` 可能产生消息、审批或用量冲突，不能当作幂等重试接口 |
| `apps/buddy/service/src/storage/database.ts`（数据库连接与事务工具） | `withTransaction()`（事务函数）直接开启事务，不能在外层再套同类事务来提交检查点 |
| `apps/buddy/service/src/BuddyService.ts`（后台业务服务） | 历史重放后仍有中断任务恢复及 `compactTerminalRuns()`（终态日志压缩函数）；优化后的总耗时需包含这些后续工作 |
| `apps/buddy/src/app/bootstrap/useDesktopLifecycle.ts`（前端启动协调器） | 等待运行时连接就绪，再恢复工作区、准备界面，成功后结束加载状态 |

已确认全量重放位于日常启动路径，而非仅安装后首次执行。

**重要限制：** 当前事件恢复以会话、分支和运行基础记录仍在数据库中为前提。事件投影器不负责创建这些完整基础记录。能重建事件投影，不等于能从事件日志重建整个数据库。

## 3. 首期需求边界

**包含：**

1. 补充恢复细分耗时及工作量指标。
2. 为可信恢复结果建立持久化检查点。
3. 稳定且可信的历史运行记录跳过全文读取及重建。
4. 新增、变化、未结束、异常或不可信的运行记录，沿用既有完整读取、修复和重建流程。
5. 保留启动一致性屏障、中断恢复、错误诊断和强制完整校验入口。
6. 验证检查点迁移、崩溃、压缩、删除、投影规则升级和投影丢失情形。

**不包含：**

- 真正按字节偏移读取日志尾部，或只投影检查点之后的事件。
- 为首期全面改造 `project()` 的重复执行语义；故障重试复用已有完整重建路径。
- 后台恢复、并行全量重放、全面调整启动生命周期或前端加载逻辑。
- 独立快照文件、尾部索引、通用同步框架或新的事件投影引擎。
- 仅凭“任务已结束”、文件大小或修改时间就判定数据可信。
- 从日志自动创建数据库中不存在的运行记录，或承诺恢复整个丢失的数据库。
- 云端同步、清理历史来提速，或提前隐藏加载动画。

## 4. 推荐方案

### 4.1 首期只提供两条恢复路径

1. **可以证明符合跳过条件：** 跳过该运行记录的事件正文读取和数据库重建。
2. **其余情况：** 对该运行记录完整读取、校验、修复并重建；失败则沿用现有错误处理。

即使日志只是追加了新事件，首期也完整恢复该运行记录，不另建尾部增量路径。成本从“处理所有历史事件”，变为“轻量检查已知运行记录 + 完整处理需要恢复的记录”。

启动步骤：

1. 批量取得已知运行编号、会话映射、运行状态及检查点，再获取必要文件元数据。避免每个编号额外查询一次所属会话。
2. 未结束或异常任务优先完整恢复，之后继续沿用既有中断处理。
3. 稳定终态记录仅在检查点可信、投影版本兼容、轻量文件标识匹配、且不存在已知数据库异常时跳过。
4. 缺少检查点、标记已失效、文件变化、版本不兼容、已知投影缺失等情况完整恢复。文件缺失沿用现有恢复或错误语义，不自动视为稳定。
5. 完整恢复成功时，在投影事务中建立新检查点；跳过时使用可信检查点初始化下一事件序号，防止首次追加又全文读取。
6. 完成必需恢复后，按原流程初始化服务和前端，不提前宣布就绪。

保留 `replay()` 作为强制完整重建路径；启动按变化恢复的接口需与它区分，不能让诊断请求意外走跳过路径。

后续启动压缩也要复用本轮“已验证无变化”的判断，不能对刚跳过的稳定记录无条件再调用全文读取修复。需要压缩的变化记录继续沿用既有压缩流程；压缩规则改变时使相关判断失效。此协调留在事件模块内部，不要求前端了解压缩或检查点细节。

### 4.2 检查点与最小写入协议

首期检查点优先保存在现有数据库内，不新增独立快照或清单文件。每个运行记录至少需要：

| 信息 | 用途 |
|---|---|
| 运行编号 | 关联已有运行记录；物理删除时可随其清理 |
| 完整恢复确认的最后事件序号 | 初始化下一事件序号；压缩保留原序号且可能有间隔，不能用事件条数代替 |
| 投影规则版本 | 规则不兼容时失效；不把所有无关数据库迁移都当作投影规则改变 |
| 恢复时取得的轻量文件标识 | 判断明显追加、替换、截断等变化；具体字段需按平台验证，不等于正文完整性证明 |
| 可信状态 | 区分已可靠恢复、已失效或尚未建立检查点 |

**首期推荐保守维护方式：只有完整恢复成功后才发布可信检查点。** 正常追加投影继续使用现有流程，不必每批事件都刷新可信检查点；发生变化后，下次启动完整恢复一次，再建立新标记。

必须满足以下顺序：

- **受管修改前先失效：** 任何可能改变日志的追加、替换、压缩、修复，都要先持久化撤销可信标记，再修改文件。首期保守地执行检查点删除语句；检查点已不存在时，不会新增可信状态写入，但仍有数据库语句调用成本。该成本尚未进行独立性能测量。
- **失败则停止修改：** 失效标记提交失败，不允许继续修改日志。不能先替换文件、事后才通知检查点失效。
- **恢复时原子发布：** 完整重建的投影更新与对应可信检查点，在投影器内部的同一个数据库事务中提交。文件修复及必要持久化未成功，不得发布可信标记。
- **不套嵌套事务：** 在既有投影器的事务边界内增加检查点提交，不在 `RunEventLog` 外层套另一个 `withTransaction()`。
- **同一运行串行：** 文件观察、恢复和修改复用现有按运行记录的队列，避免恢复期间日志又被修改。

`readAndRepair()` 可能修改文件，不能将它一律当作只读操作。首期允许保守地在调用可能修复的路径前失效，即使最终没有修复；不要为了少一次重建引入复杂回调或跨层数据库访问。

这样，即使“标记已失效、日志已落盘、投影未提交”时崩溃，下次也会完整恢复。恢复事务失败时，投影与新检查点一起回滚；重复完整恢复不重复产生业务记录，需由现有恢复测试验证。

### 4.3 模块职责与解耦要求

| 模块 | 首期职责 | 不应承担的职责 |
|---|---|---|
| `RunEventStore`（日志文件存储器） | 文件元数据、读取修复、追加、替换与持久化 | 直接查询或写入检查点数据库 |
| `RunEventProjector`（数据库投影器） | 投影重建、检查点持久失效、投影与可信检查点原子提交 | 枚举文件、控制前端启动 |
| `RunEventQueries`（事件查询器） | 批量提供运行信息与检查点读取结果 | 执行文件修改或恢复调度 |
| `RunEventLog`（事件日志协调器） | 判断跳过或重建，先失效再调用文件修改，维护串行队列及下一序号 | 外包一层数据库事务、复制投影规则 |
| 启动入口与前端 | 等待恢复完成，沿用现有就绪及失败语义 | 了解检查点表、文件标识或失效细节 |

优先扩展现有端口和组装函数，只有需要隔离复杂判断时才提取小型纯函数；不为首期新增通用恢复服务体系。日志修改必须经过协调器或具备等价的持久失效协议，不能留下绕过检查点的受管写入入口。

### 4.4 完整性与数据库恢复边界

**日常轻量检查能保证的范围：** 已审查的受管修改先失效；明显文件变化、版本变化、未结束任务及已知投影异常不会被跳过。

**日常轻量检查不能证明的范围：** 文件标识不变的外部正文改写、静默损坏，或未通过受管入口修改的数据库投影内容。检查点不是防篡改凭证；不得宣称每次启动都能发现任意旧事件修改或任意投影行缺失。

- 已提供受控的强制完整读取、校验和重建入口：启动前设置环境变量 `LEXORA_BUDDY_EVENT_RECOVERY=full`（强制完整恢复开关），或调用 `recoverAll({ force: true })`。Electron 仅透传值为 `full` 的开关；删除该环境变量后恢复默认跳过策略。该入口用于疑似损坏、人工编辑、备份恢复及诊断场景，不删除历史数据。
- 已发现投影缺失或损坏时，先使对应检查点失效，再定向完整恢复；数据库级异常或受管备份恢复可以整体失效。
- 数据库备份携带旧检查点时，不能只靠数据库自身版本号证明其有效。受管恢复必须失效检查点；外部拷贝恢复若无法可靠识别，需使用强制完整校验，不承诺自动识别。
- 如现有存储承诺要求“每次启动全文校验所有历史”，则轻量跳过不能在保持该保证的前提下启用；实施前须核实此约束，不把完整性保证的变化隐藏为纯性能改动。
- 数据库中的会话、分支和运行基础记录存在时，可以重建事件投影。基础记录缺失或数据库整体丢失时，诊断并走单独恢复流程，不自动插入未知运行记录，也不宣称本方案可完整恢复。
- 遵守既有删除语义。当前会话删除使用软删除标记，不能把它误当作物理删除；物理删除运行记录时清理检查点，不通过目录扫描自动复活已删除数据。
- 直接修改投影字段的业务路径、迁移及修复操作须审查其是否使检查点失效。数据库并非所有字段都只由事件投影器写入，不能默认日志未变就代表所有数据库状态未变。

周期性全文校验与后台校验不属于首期；是否需要它们，在轻量检查的保证边界与首期测量明确后单独决定。

## 5. 备选方案与取舍

| 方案 | 评价 |
|---|---|
| 稳定历史跳过 + 变化记录完整重建 | 首期唯一推荐；复用现有恢复，改动较小、故障回退明确 |
| 检查点 + 真正尾部增量恢复 | 后续候选；仅在变化记录完整读取仍是显著瓶颈时设计，需验证定位、顺序及重复投影语义 |
| 独立快照 + 增量重放 | 增加版本、失效及恢复管理；首期不新增 |
| 并行全量重放 | 不减少总工作量，可能增加数据库竞争和磁盘压力；不作为首选 |
| 恢复全部后台执行 | 可能先显示不一致数据，还增加并发、取消与错误反馈复杂度；首期不采用 |
| 调整动画或提前隐藏 | 不解决瓶颈；不采用 |

## 6. 实施步骤与可回退性

1. **建立基线：** 同一目标构建、机器和数据集，测量空数据、稳定历史、变化记录和异常中断启动。
2. **补充计时：** 分开测量枚举、文件检查、读取校验、数据库重建，以及后续中断恢复和压缩。
3. **审查写入边界：** 列出追加、替换、修复、删除、迁移及直接修改投影的入口，确定最小检查点结构、文件标识和版本规则。明确第 4.4 节的保证边界后才启用跳过。
4. **先实现安全回退：** 完成持久失效及投影与检查点原子提交；先在强制完整恢复模式验证崩溃窗口，再启用跳过。
5. **首轮迁移：** 旧记录没有检查点，进行一次完整恢复；该次启动仍可能较慢。数据库基础记录缺失不视为普通检查点迁移。
6. **验证速度与一致性：** 同一受支持数据集，对照跳过恢复与强制完整恢复的结果。保留既有软删除、中断恢复及消息引用语义，不只比较速度。
7. **决定是否继续：** 首期达标则结束；仅当剩余耗时证明确有必要，才单独设计真正尾部增量或非关键工作后台化。

回退开关关闭“跳过”策略即可恢复完整重建，可信标记不能阻止强制重建。回退不删除日志、对话或凭据。若新增数据库表或迁移，不默认保证旧安装包可读取新结构，降级兼容性单独验证。

## 7. 指标与验收标准

### 7.1 观测要求

记录总启动耗时、历史恢复耗时，以及枚举、轻量检查、全文读取校验、投影重建的分段耗时；统计检查、跳过、完整重建、失败及读取事件数量。首期不设置“尾部增量恢复数量”，以免指标误导。

另记录后续中断恢复、日志压缩及可信标记失效成本。测量正常任务追加是否退化，避免启动变快却让每批事件多一次数据库提交。

日志只保存必要技术元数据，不新增对话正文、事件正文、凭据或个人绝对路径。

### 7.2 性能验收
