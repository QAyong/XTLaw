### 使用场景与问题 / Use case and problem

**场景：音视频播放插件里的“让 Agent 写纪要”。** 播放插件右侧有一页“智能纪要”。我希望点一下按钮，当前聊天里的 Agent 就根据文字记录写纪要，并交回插件显示。

**更一般的需求：** 插件界面里的一个按钮，意思是“让 Agent 现在处理这份材料”。例如：表格插件里“分析选中的区域”，PDF 插件里“总结这一页”，文字稿插件里“写纪要”。用户已经在插件里选好了材料，不想再切回聊天、粘贴、输入提示词、点发送。

**现在做不到的原因（读代码得出）：**

- 插件的 `references.add` / `references.capture` / `references.commit` 只把材料放进输入框草稿，不发送。用户还要回到聊天再点一次发送。
- `agent.actions` 在旁边独立执行，不会向主对话发消息，也不会占用主对话里正在用的 Agent 和工具。
- `models.generateText` 是插件自己的无工具模型调用，没有当前对话上下文，也不能调用 Agent 的工具把结果写回插件。
- 聊天发送路径（`chat.startTurn`、`chat.queue.enqueue`）以草稿为入口：入参是 `draftId` 和 `expectedRevision`，发送时从草稿读正文、参与者、模型选择，成功后清空草稿。插件没有办法在不改动用户草稿的前提下发一条消息。

### 期望的体验 / Desired outcome

1. 插件在清单里声明一条或多条固定消息，例如 `{ id, title, text }`。`text` 在安装时就写死，运行时不能改、不能拼接。
2. 视图里用户点击插件自己的按钮后，插件调用一个新方法，把某条已声明的消息提交到**用户选定**的聊天。
3. 聊天里只出现**一个**普通用户气泡，正文就是声明里的 `text`，和用户手打再点发送一样，不加来源标签、不加隐藏前缀。随后 Agent 按普通对话处理，用户可以阅读，也可以停止这一轮。
4. 可以附带这次点击已经取得的引用（沿用现有引用的授权和限额）。超限就整次失败，不截断，不改成不带引用的消息。
5. **不动用户正在写的草稿**：不插入、不清空、不把草稿一起发出去。
6. 有多个聊天时必须由用户选，不能猜。没有可接收的聊天，或目标正在回复、已有排队输入时，明确失败，**不入队**。入队会让一次点击几分钟后突然开始。
7. 后台不能触发：任务事件、`agent.actions`、`agent.tools`、定时命令、插件入口 `activate` 都不能调用，只允许前台可见且持有焦点的交互视图。
8. 需要单独的安装授权。确认页要展示每条声明的标题和完整正文，用户看不到正文就不能确认。

### 当前做法或替代方案 / Current workaround or alternatives

- 把提示词放进草稿，让用户自己再点一次发送。多一步，而且用户草稿里本来有内容时会冲突。
- 插件用 `models.generateText` 自己写。没有对话上下文，写不回插件，也不是用户在聊天里用的那个 Agent。
- 在插件界面上提示“请到聊天里输入……”。用户要自己写提示词。

### 补充材料 / Additional context

**我们尝试过自己做，评估后放弃（读代码得出，基于 upstream/master `f0228448`，未实现、未运行）：**

最大的改动在发送路径，不在插件接口。要做到“不动草稿地发一条消息”，大致要：

1. 服务端为 `ChatTurnService.prepareStart` 增加不依赖草稿的入口，由内存里合成的输入提供正文和引用，并跳过“发送成功后清草稿”。现在 `prepareStart` 里读 `draft.content`、`participants`、`modelSelection`、`executionConfig` 的地方有好几处。
2. 每个会话分支只允许一份草稿（`composer_drafts` 上有按 `conversation_id, branch_id` 的唯一索引），所以不能为这条消息另建一份草稿。
3. 前端 `useChatTurnExecution.send` 的第一步就是 `drafts.setUserContent`，会覆盖用户草稿；不能直接复用。
4. 如果走“先保存草稿、替换内容、发送、再恢复”这条近路，用户此刻正在打字、发送失败或窗口切换时会丢草稿，我们不建议。

这是核心发送链路，改动面大，也牵涉维护者对草稿模型的设计意图，所以我们没有在下游分叉里单独做，想先听维护者的意见。

**一种可行的接口形态（供维护者取舍，不要求按此实现）：**

```jsonc
// 清单
"permissions": { "composerSubmit": true },
"contributes": {
  "composerSubmits": [{
    "id": "<plugin-id>.write-summary",
    "title": "写智能纪要",            // 只在安装确认页显示
    "text": "请根据引用的文字记录写智能纪要，并写回播放器。"
  }]
}
```

```ts
// 视图里，用户点击之后
const { targets } = await context.composer.listTargets()   // 只返回 { id, label }
const result = await context.composer.submit({ id, targetId, quotes })
// result.status: 'submitted' | 'retry' | 'rejected'，reason 用来选提示文案
```

- `listTargets` 的目标集合可以直接复用现在“引用到聊天”能接收引用的那批聊天。我们倾向第一版只列已有会话的窗格，新任务窗格（还没有会话）先不列，否则要先建会话。
- 一个很小的权限就够：只允许提交本插件已声明的消息，并允许附带引用。不包含读文件、写草稿或调用模型。
- 返回只分三类：成功、让用户重试或重选（目标忙、没有目标、视图不可见）、拒绝（引用超限、未授权）。

**我们特意去掉的东西（评估后认为过度）：**

- 点击凭证（“申请一次性凭证再提交”）。宿主看不到浏览器内部的用户激活标记，脚本也能随时申请凭证，防不住已聚焦视图里的脚本，只会增加状态。
- 独立的频率冷却。提交成功后目标进入“正在回复”，下一次点击就会因目标忙被拒，已经是自然限流。
- 来源标签和隐藏前缀。正文在安装确认页已完整展示，用户点击前就知道会发出什么。

**没有验证的地方：**

- 以上全部是读代码和讨论得出的设计，没有实现、没有运行。
- 没有确认“前台可见且持有焦点”在各平台上的行为是否一致；目前扩展桥拿不到真实鼠标事件，这一条只能限制后果，不能证明调用来自真实点击。
- 去掉来源标签后，事后从聊天记录里看不出这句话是插件代发的。如果维护者认为需要追溯，可以再加。
- 附带的引用由插件提供，宿主只能校验形状、限额和文件版本，不能验证内容是否忠实。引用会随消息显示在聊天里。

示例只涉及通用的音视频和文档场景，不涉及真实内容。
