# Spec-008：点击停止立即结束聊天运行展示

**日期：** 2026-09-29  
**状态：** 已实现；2026-10-09 集成上游队列保护并通过定向自动验证，待桌面手动验收

**首版分支：** `codex/instant-chat-stop`；本次集成提交在当前 `master`

**行为修订：** 取消待处理期间的新旧消息均暂停，取消完成后不自动继续；本次不再采用首版“停止后新提交消息自动衔接”的规则。

## 1. 背景

AI 正在调用工具或执行命令时，原来的停止流程会等待后台中断及清理完成，输入框才恢复发送按钮。用户容易认为点击无效，连续点击几次。目标是获得类似 XTLaw 的操作感受：点击后立即停止当前运行展示，可以继续输入和提交下一条消息。

## 2. 已实现的行为

- 点击停止时，同步把当前轮次的展示标记为已取消，输入框恢复发送按钮。
- 保留点击时已经生成的部分回答，停止等待授权及运行中工具的展示。
- 在后台收尾期间，冻结该轮次的消息和事件展示，迟到的输出不会让界面重新进入运行状态。
- 仍立即调用已有后台取消接口；后台真实执行状态继续保留，直到中断和清理结束。
- 收尾期间发送的新消息通过已有队列接收并清空已提交的草稿；新消息保留为暂停状态，取消成功后不自动启动。
- 停止前已有的排队消息和取消待处理期间新提交的消息均暂停，需通过队列操作明确继续。
- 暂停保护针对取消待处理窗口及这次暂停的队列，不表示停止结束后所有新的消息都必须手动继续。
- 取消请求失败时，恢复真实运行展示，并在仍停留于原会话时显示错误。
- 后台真实终态到达后，以后台记录替换临时展示；切换会话时不会把旧会话的临时内容带入新会话。

## 3. 方案与边界

本次把“用户看到的运行状态”和“后台是否释放执行”分开。前者立即取消，后者仍沿用现有中断流程。下一轮调度、权限和分支操作仍依据真实执行状态判断。

XTLaw 通过前端临时展示提前响应点击，后台取消接口仍等待真实中断和清理；不保证操作系统中的命令进程在点击瞬间完成退出。

停止 RPC 统一经 `ChatQueueService.cancelRun()` 进入队列保护：同一运行的取消请求去重，取消前后暂停队列，在派发、steer、follow-up 及异步校验后重复检查取消状态。旧运行的取消不能暂停较新运行的队列；取消失败须释放保护。沿用既有进程终止策略和命令超时，不因界面立即停止而绕过真实执行状态。

## 6. 限制与未决事项

界面立即停止不代表进程已经退出；真实清理耗时由已有后台实现决定。取消失败或后台拒绝明确继续时，队列及错误信息仍遵循现有处理。本次自动检查覆盖取消期间新旧消息暂停及不自动继续，尚未通过实际桌面操作验收连续提交多条消息的行为。
