## 背景

法律工作场景下，案卷材料（起诉状、证据清单、合同等）含大量真实身份信息，直接交给 AI 处理存在保密风险。用户需要的流程是：

1. 把材料放进项目
2. 本地脱敏，生成“脱敏件”
3. 后续 AI 对话只读取脱敏件
4. AI 依据脱敏件生成新文件
5. 生成的文件可**还原**为含真实姓名的版本

核心矛盾：用户希望材料就放在项目文件夹里（便于管理、备份、同步），但 AI 的工具以工作区为根，能读到工作区内的任何文件。

本规格解决这一问题，并明确其能力的**边界**。

***

## 需求边界

**包含：**

* 用户把材料放入项目内的投入口目录后，插件自动发现并提示
* 插件将原件**移出到工作区之外**的“真名区”，并在项目内生成脱敏影子件
* 插件通过项目指令文件让 AI 自动知道应使用脱敏件
* 提供“并排复核”界面，供人工确认脱敏结果
* 对 AI 生成的文件提供一键还原，还原产物落在真名区
* 映射表（占位符与真实值的对应关系）可导出备份

**不包含（防止范围自行扩张）：**

| 不做的事                  | 原因                                   |
| --------------------- | ------------------------------------ |
| 对话脱敏（在发送前拦截并改写内容）     | 现有扩展钩子存在覆盖缺口且失败即放行，不能作为保密底线，详见“安全边界” |
| 扫描件 PDF 的 OCR（光学字符识别） | 独立工作量，留待第二版                          |
| 多人协作、云端同步             | 本版面向单机单案                             |
| 自动上传、自动调用外部 AI 服务     | 与保密前提冲突                              |
| 对原件做加密存储              | 经评估为过度设计，改用“物理移出”，决策记录见“安全边界”        |

***

## 核心模型：两区分离

**一句话规则：真名相关的全部在工作区之外，AI 能读的全部在工作区内。**

### 三个区域

| 区域        | 位置                                      | 内容            | AI 可读 |
| --------- | --------------------------------------- | ------------- | ----- |
| **真名区**   | 工作区之外（用户指定）                             | 原件、映射表        | 否     |
| **脱敏区**   | 项目内 `脱敏/` 目录                            | 影子件、AI 生成件、索引 | 是     |
| **插件私有区** | 由 `pi.plugin.getDataPath()`（插件私有目录接口）给出 | 真名区路径、插件配置    | 否     |

### 目录结构

```text
真名区（工作区之外）
案卷-张三诉李四/
├── 起诉状.docx          原件（原封移出）
├── 证据清单.pdf
└── _映射表.json          甲某某 = 张三（真实姓名全部在此）

项目工作区
案卷项目/
├── AGENTS.md            项目指令（插件维护其中一段）
├── 待脱敏/               投入口（唯一被监听的目录）
└── 脱敏/
    ├── 起诉状.docx       影子件（AI 使用）
    ├── 答辩意见.docx     AI 生成件（内容为占位符）
    └── _索引.json        只列影子件，不含真名区路径
```

### 三条硬规则

> 以下三条是本方案成立的前提，不是可选项。原因见“安全边界”一节。

1. `AGENTS.md`（项目指令文件）只写“材料一律使用 `脱敏/` 目录”，**不得出现真名区路径**。
2. `_索引.json` 及任何影子件的元数据**不得包含真名区路径**。
3. **映射表绝不放进工作区**——它本身就是一份真实姓名清单。

## 场景描述

### 正常流程

1. 用户首次在该项目打开插件 → 插件要求用户选择一次真名区目录，记入插件私有设置
2. 用户把材料拖入 `待脱敏/` → 后台服务发现新文件，提示“发现 3 个文件，是否脱敏并移出？”
3. 用户点击确认 → 插件复制文件到真名区 → 校验完整性 → 从项目移出（进入系统回收站，可恢复）
4. 插件生成影子件写入 `脱敏/`，并更新 `_索引.json` 与 `AGENTS.md` 中的受管段落
5. 用户在面板中并排复核原文与影子件，逐条确认实体
6. 用户与 AI 对话 → AI 依据 `AGENTS.md` 的指引读取 `脱敏/` 中的影子件；也可用 `@` 引用
7. AI 生成成果文件，落在 `脱敏/` 内，内容仍是占位符
8. 用户点击“还原” → 插件用映射表反向替换 → 真名版写入真名区（工作区之外）

### 异常流程

| 异常情况                        | 系统应有的兜底行为                        |
| --------------------------- | -------------------------------- |
| 真名区目录不可写或不存在                | 中止移出，**不删除**项目内原件，并提示用户重新选择目录    |
| 跨盘移动失败（如 D: 到 C:）           | 采用“复制 → 校验 → 删除”三步；任一步失败即保留原件并报错 |
| 脱敏过程中应用崩溃                   | 原件仍在项目内（尚未移出），可重新执行，不产生半成品影子件    |
| AI 改写了占位符（如 `甲某某` 写成 `甲先生`） | 模糊匹配还原，并把不确定项列出供人工确认，不静默处理       |
| AI 自创了不在映射表内的名字             | 保持原样并标记，提示无法还原                   |
| 映射表丢失或损坏                    | 影子件无法还原；插件应提示并要求从备份恢复            |
| 用户误把大量非材料文件放入投入口            | 移出前必须经用户确认；监听范围限定在投入口目录内         |

| 让 AI 自动认路 | 插件维护工作区根 `AGENTS.md` 的受管段落                                              | `fs.write`           |
| 提示与通知     | `pi.ui.showToast` / `pi.ui.notify`                                      | `notify`             |

### 插件形态选择

**采用：普通面板插件 + 一个后台服务。**

**不采用 `contributes.agentExtensions`（agent 扩展钩子）。** 理由见“安全边界”一节第 2 小节。

### 为什么用 `AGENTS.md` 让 AI 自动认路

运行时会把工作区根的 `AGENTS.md` 读入 AI 的系统提示（依据见附录 A.4）。因此插件只需维护其中一段受管文字，AI 就会自动知道“材料应使用 `脱敏/` 目录”。

* 优点：**完全不依赖任何钩子**，不会因为某条出站路径没有钩子而失效
* 实现要求：写入时必须保留用户已有内容，只增删由插件管理的段落（建议用明确的起止标记包裹）

## 脱敏规则集

分三级，可靠性与自动化程度递减。

| 级别     | 对象                              | 方式               | 可靠性  | 是否自动 |
| ------ | ------------------------------- | ---------------- | ---- | ---- |
| **L1** | 身份证号、手机号、统一社会信用代码、银行卡号、案号、邮箱、车牌 | 纯规则（正则表达式 + 校验位） | 高    | 全自动  |
| **L2** | 人名、机构名、地址                       | 小模型识别 + 人工逐条确认   | 中    | 半自动  |
| **L3** | 化名、简称、姓名恰为普通词                   | 人工补充             | 依赖人工 | 手动   |

### 设计原则

* **L2 阈值宁低勿高**：宁可多报。误报的代价是用户多点一下；漏报的代价是泄露一条真实信息。
* **规则优先**：L1 类信息有确定格式与校验位，规则引擎的准确率高于任何模型，且零模型依赖、零额外性能开销。
* **角色词锚定**：优先利用法律文书结构（`原告`/`被告`/`第三人`/`证人` 标记、落款签名区），比纯模型识别更可靠。
* **不可全自动的部分**：中文人名识别是整条链路的薄弱点，必须保留人工确认环节。

### 小模型的选型约束（第二版确定）

用户场景以笔记本为主，约束为：**全平台通用、CPU 可运行、内存占用小**。

* 优先 ONNX（开放神经网络交换格式）量化模型 + `onnxruntime`（跨平台推理运行时，含 ARM 预编译包）
* 或走浏览器内推理（插件面板本身即 Chromium 内核），可做到零额外运行时依赖
* 排除需要显卡或数百 MB 以上内存占用的模型

## 占位符与映射表

### 占位符规则

| 规则      | 示例                | 说明                 |
| ------- | ----------------- | ------------------ |
| 保留实体区分度 | `原告甲某某` / `被告乙某某` | 不做简单删除，保留实体个数与相互关系 |
| 角色词锚定   | `原告甲某某`           | 保留法律角色，材料可分析性高     |
| 全局一致    | 全项目内 `甲某某` 始终指同一人 | 保证跨文件可交叉引用         |

> 反面做法：直接删除，或统一替换为“某人”。这会破坏材料的可分析性，AI 无法判断“甲”和“乙”是两个不同主体。

### 映射表结构（草案）

```json
{
  "version": 1,
  "caseName": "张三诉李四",
  "createdAt": "2026-09-15T10:00:00+08:00",
  "entities": [
    {
      "placeholder": "甲某某",
      "real": "张三",
      "type": "person",
      "role": "原告",
      "source": "L2:ner+manual"
    }
  ],
  "processedFiles": [
    {
      "shadow": "脱敏/起诉状.docx",
      "original": "起诉状.docx",
      "rules": ["L1:idcard", "L1:phone", "L2:ner"],
      "redactedAt": "2026-09-15T10:05:00+08:00"
    }
  ]
}
```

### 维护要求

* **必须支持导出备份**：映射表丢失意味着影子件永久无法还原
* **存储位置**：真名区内（与原件同区），**不在工作区**
* **写入方式**：原子写（先写临时文件再整体替换），避免中途失败损坏映射表

## 还原流程

| 情况              | 处理方式                       |
| --------------- | -------------------------- |
| 正常占位符           | 直接反向替换                     |
| AI 改写了占位符       | 模糊匹配还原；不确定项列出供人工确认，不静默处理   |
| AI 自创、不在映射表内的名字 | 保持原样并标记，无法还原               |
| 触发方式            | **手动点击按钮**，不做自动还原          |
| 还原产物落点          | **只写真名区，绝不写回工作区**          |
| 处理范围            | **只处理用户点选的文件**，不批量扫描 `脱敏/` |

### 为什么必须是手动还原

若在 AI 每次写文件后自动还原，真名版就会出现在工作区，下一轮对话中 AI 即可读到，前面的脱敏工作全部失效。这是本方案中最容易做错、后果最严重的一处。

### 为什么只处理点选文件

`脱敏/` 目录同时存放影子件（输入）和 AI 生成件（输出）。批量还原会把影子件也还原成真名版并留在工作区，同样造成泄露。

## 安全边界与已知限制

> 本节是本方案能否成立的真正前提，请重点审阅。

### 1. 方案靠什么成立：路径不泄漏

方案**不是**靠“工作区边界”成立，而是靠**真名区路径不泄漏**。

**依据**：在 `Auto`（自动允许）权限模式下，AI 使用显式路径读取工作区之外是**被允许的**（依据见附录 A.3）。也就是说，工作区之外并非天然隔离区，只是“AI 不知道就不会去读”。

**推论**：只要真名区路径泄漏一次，本方案的隔离即失效。因此“三条硬规则”是硬约束。

**补充建议**：案卷类项目建议使用 `ask`（每次询问）或 `accept-edits` 权限模式，而非 `Auto`。

### 2. 为什么不使用 agent 扩展钩子做拦截

经代码核实，现有扩展钩子存在三个缺口，**不能作为保密底线**：

| 缺口                   | 依据                                                           | 后果                       |
| -------------------- | ------------------------------------------------------------ | ------------------------ |
| 子代理路径未包装             | `packages/agent-runtime/src/subagent-model-binding.ts:87-94` | 经 `Task` 委派的子代理出站内容不经过钩子 |
| 一次性补全未包装             | `packages/agent-runtime/src/one-shot-complete.ts:110-114`    | 提示增强、标题生成等出站内容不经过钩子      |
| **失败即放行**（fail-open） | `packages/agent-runtime/src/extensions/runner.ts:423-436`    | 钩子处理器抛错或超时后，按未修改的内容继续    |

第三点最关键：钩子处理器出错或超时（上限 30 秒，见 `packages/shared/src/trusted-extensions.ts:144`）时，**原文照常发送**。把保密底线建立在“失败即放行”的机制上不成立。

因此本版只做**文件脱敏**（离线、可复核、可重跑），不做对话脱敏。

### 3. 残余风险清单

| 风险                    | 说明                                   | 缓解措施                        |
| --------------------- | ------------------------------------ | --------------------------- |
| `Auto` 模式下路径若泄漏即可被读   | 隔离依赖路径保密                             | 三条硬规则；建议使用 `ask` 模式         |
| 脱敏过程中明文存在于插件进程内存      | 无明文则无法脱敏，不可避免                        | 仅存在于本地进程，不向外发送              |
| 影子件本身是明文              | AI 必须能读，属设计使然                        | **脱敏质量才是真正的防线**             |
| 用户自己在对话中直接输入真实姓名      | 任何方案都无法拦截                            | 可选的发送前提示（第二版）               |
| 移出后原件位置变化，用户可能误以为文件丢失 | 体验问题                                 | 面板显示状态；`fs.remove` 进入回收站可恢复 |
| 重识别风险（去标识化不等于匿名化）     | 例如“独女 + 唯一继承人 + 某上市公司董事长”的组合仍可反推到特定人 | 任何工具都无法解决，需人工判断             |

> **核心结论**：移出机制保护“原件不被误读”，脱敏质量保护“交给 AI 的内容不泄露”。两件事都要做，缺一不可。

### 4. 关于加密方案的取舍（设计决策记录）

早期曾考虑对原件做 AES-256-GCM（一种带认证的对称加密算法）加密后仍留在项目内。经评估**放弃**：

| 对比项    | 加密方案               | 移出方案             |
| ------ | ------------------ | ---------------- |
| 防护强度   | 强（不受权限模式影响）        | 中（依赖路径保密）        |
| 复杂度    | 高：密钥管理、口令交互、密钥备份   | 低                |
| 数据丢失风险 | **高**：密钥丢失则原件永久不可读 | 无（原件仍是原件）        |
| 用户心智   | 复杂                 | 简单：“真名在外面，脱敏在里面” |

**结论**：加密解决的是“AI 主动翻找”这一低概率场景，代价却不小；移出方案已覆盖实际威胁模型（误读、误传、误备份）。若未来需要更强保证，可在此基础上叠加加密，两者不冲突。

* [ ] 材料放入 `待脱敏/` 后，原件出现在真名区，`脱敏/` 中出现对应影子件
* [ ] 项目内任何文件都不含真名区路径（可通过全量搜索验证）
* [ ] AI 在对话中读取材料时，只能读到 `脱敏/` 内的影子件
* [ ] AI 生成的文件可一键还原，还原产物落在真名区
* [ ] 还原后的真名版**不在工作区内**
* [ ] 映射表可导出备份，备份可恢复
* [ ] 异常流程（真名区不可写、跨盘失败、应用崩溃）均不导致原件丢失
