# Spec-019：文件管理器基础能力提升（最小第一版）

**日期：** 2026-10-04

**状态：** 当前 Windows 开发版功能已由用户查看并确认没有问题，用户验收通过；本轮按用户要求更新文档并提交实现。macOS/Linux 原生修改后端仍待实现，不标记三平台交付完成。最新验收与乱码修复记录见第 13 节，第 10—12 节保留各阶段历史。

**目标：** 快速完成现有文件树的“创建 → 编辑 → 重命名 → 删除”闭环，不重做工作台，不引入完整 IDE 或通用文件操作框架。

## 1. 背景与取舍

已有目录树、分页读取、手动/窗口聚焦刷新、文本编辑与保存冲突检测、Markdown/图片预览、系统定位和文件选区引用。本期补充文件整理能力，不做 Git 集成或更多格式预览。

以下为当前实现的边界；已打开文件操作见第 3.4 节：

- 干净或未保存的已打开文件允许重命名；正在加载/保存的副本返回忙碌，稍后重试。移到回收站时，未保存内容必须由用户选择保存、放弃或取消。
- 重命名成功后迁移编辑副本、工作台资源路径、标签标题及目录标签的当前路径，保留本地未保存内容和保存冲突；旧历史引用不改写。
- 重命名后移除旧目录范围的展开记录，不迁移全部展开路径；保留不相关目录的展开状态。
- 复用现有树刷新。当前目录立即刷新，其他关联标签标记过期并在激活时刷新，不先建设全局目录缓存系统。
- 第一版不支持仅大小写重命名，明确提示，不实现临时名称及恢复流程。
- 不新增全局操作协调器、通用范围锁或调度框架。使用普通目录容器的小型操作模块和必要的编辑入口保护。
- 按 Windows、macOS、Linux 三平台设计和交付，不将 Windows 专用机制写入公共业务接口。分平台实现和验收；尚未实现或验证的平台明确标记，安全底线不因平台差异而降低。

本文描述交付要求，不把代码阅读、构建成功或模拟测试等同于功能验收。

## 2. 第一版功能与菜单

| 对象 | 打开/新建 | 修改 | 路径/系统定位 |
|---|---|---|---|
| 文件 | 打开 | 重命名；移到回收站 | 复制相对路径；复制完整路径；在系统文件管理器中显示 |
| 文件夹 | 新建文件；新建文件夹 | 重命名；移到回收站 | 复制相对路径；复制完整路径；在系统文件管理器中打开 |
| 根目录/树空白处 | 新建文件；新建文件夹 | 刷新 | 在系统文件管理器中打开根目录 |

- 菜单每次操作一个条目，复用现有菜单和主题，不做视觉重设计。
- 共用树只发可选菜单事件，普通目录容器装配功能；技能树和历史变更树保持只读。
- 文件“打开”复用现有左键路由，不启动系统默认应用。
- 右键捕获实际条目，不自动打开编辑器；空白处目标是根目录，不猜测之前选中的文件。
- 切换标签、空间或授权时关闭菜单/输入框，未提交的旧目标失效；已提交结果只反馈给原目录。
- 相对路径相对于授权根目录，使用 `/`；完整路径由可信层解析。
- 根目录不允许重命名或删除，但允许在授权根目录内创建子项。
- 无效或不受支持的链接条目不提供写操作；不显示尚未实现的灰色占位功能。
- 保留键盘菜单入口（Shift+F10/菜单键）、方向键、Enter、Esc 和焦点返回；不新增 Delete/F2 快捷操作。

## 3. 操作行为

### 3.1 新建文件/文件夹

1. 使用轻量名称对话框，显示创建位置、自动聚焦，只接收单个名称，不接受多级路径。
2. 创建文件为零字节普通文件，不自动追加扩展名或模板；采用排他创建，不覆盖已有条目。
3. 名称错误就近提示，服务端再次校验；重名以实际操作结果为准。
4. 成功后展开父目录、刷新并选中新条目；可编辑文件走既有编辑路由。文件夹不强制展开自身。
5. 创建成功但打开/刷新失败时明确提示“已创建，但打开/刷新失败”，不诱导重复创建。

### 3.2 重命名

1. 使用同一名称对话框，显示原名称和父目录；文件可选中主文件名，扩展名可修改并给出影响提示。
2. 名称完全不变时关闭，不写磁盘；仅大小写变化明确拒绝。
3. 文件和目录都不覆盖已有目标，包括不同类型的同名条目。
4. 检查整个目标范围，操作期间阻止新的打开、编辑、保存和关闭；忙碌副本拒绝操作。已打开的干净/未保存副本均可迁移，目标路径已有编辑资源时明确拒绝。
5. 成功后迁移所有受影响编辑副本和标签路径，清理旧范围树选择/展开记录，刷新父目录并选中新路径；不自动保存本地未保存内容。
6. 历史消息、引用快照、历史变更和导航记录不自动改写。旧目标不存在时按已有打开失败路径反馈，不创建空文件替代旧文件。

### 3.3 移到回收站

1. 每次确认，显示名称和相对位置；目录说明包含全部内容，取消为安全默认路径。
2. 对受影响未保存副本提供“保存后继续 / 放弃修改并继续 / 取消”。保存冲突或失败阻止回收；已完成的保存不声称回滚。选择放弃后仍保留编辑内容，直到磁盘回收明确成功。
3. 只有系统回收站明确成功后才关闭受影响标签、清理副本及树条目，选择仍存在的父目录，不自动打开相邻文件。
4. 失败保留文件，绝不退回永久删除；不提供永久删除、不再提示或未实现的撤销按钮。
5. 成功提示可在系统回收站恢复；确认前不递归扫描计数。
6. 回收以卷为边界判断可用性：卷是可写的本地文件系统、回收站根目录与当前用户的 `<SID>` 目录存在且归属当前用户即可执行。回收站根目录在磁盘上的存储名大小写（如 `$RECYCLE.BIN` 与 `$Recycle.Bin`）不参与判断。仅当上述条件确实不成立时失败，且失败保留文件。

### 3.4 已打开文件的重命名/回收站

**状态：已实现，当前 Windows 开发版用户验收通过。** 用户恢复实施后已接通以下流程，并于本轮确认文档下功能均已查看、没有问题。用户确认与自动化测试证据分别记录，不推断用户逐项执行了所有竞争或异常测试。

实现目标：

- 文件已打开时允许直接重命名；目录重命名覆盖已打开的子文件。
- 重命名成功后同步更新受影响标签、编辑副本与资源路径，保留未保存内容；历史消息及引用快照不改写。
- 文件/目录已打开时允许移到回收站；存在未保存修改时，明确提供“保存后继续 / 放弃修改并继续 / 取消”，不自动决定。
- 只有磁盘回收成功后才关闭受影响标签、清理经用户同意放弃的副本；明确失败时保留编辑状态。用户已主动保存的内容不声称回滚。
- 操作期间保护受影响的打开、编辑、保存及关闭流程；加载/保存中的副本、目标路径占用、外部修改冲突与结果不确定须安全处理，不产生旧路径可写入口。
- 需要补充干净/未保存副本、目录后代、多视图、取消、保存冲突、操作失败和竞争场景测试；不能仅取消现有阻止条件。

当前通过 `WorkspaceFileOperations` 接通操作期间保护、编辑副本迁移、成功后的标签批量更新与回收确认。结果不确定时保留未保存内容及备份，并维持只读保护，不能盲目重试；尚未提供自动核对结果后解除保护的界面。

## 4. 最小一致性与竞争保护

- 普通目录操作模块负责“捕获目标 → 前置检查 → 可信层操作 → 标记失效 → 刷新”，不把磁盘操作塞进共用树。
- 使用简单执行中状态防止重复提交，不建设多目标队列；请求结果不明确时先刷新核对，不盲目重试破坏性操作。
- 查询受影响资源通过小型能力接口完成，不把工作台实现细节传入平台层或文件服务。
- 重命名/删除检查与执行之间，必要的保护必须覆盖受影响资源的打开、编辑及保存入口，防止检查后重新打开/写入旧路径。单纯禁用菜单不够；保护在结束时释放。
- 存在已关闭但仍残留的干净副本时，按现有释放能力清理；未保存或忙碌副本不得静默清理。
- 路径匹配必须按目录边界（目标本身或 `目标/` 下的后代），不能用裸字符串前缀误伤相似名称。
- 当前视图复用现有 `refresh()`（刷新目录树的函数），保留不相关展开状态。其他同目录视图只标记过期，激活时刷新。
- 磁盘成功但界面刷新失败时，说明磁盘已改变，保留失效标记并提供刷新，不声称磁盘回滚。
- 保留手动/窗口聚焦刷新，不宣称自动同步所有外部修改。
- 已关闭编辑资源的旧导航记录不自动迁移；重新打开或重启恢复时沿用受限文件读取和目标校验，旧路径不能成为可保存的幽灵编辑器。

## 5. 安全底线与平台能力

### 5.1 输入与授权

- 渲染层只提交空间/目录标识、授权版本、相对路径和新名称；不接受任意绝对路径、系统命令或应用路径。
- 新建使用“父目录目标 + 单个名称”；拒绝空名称、`.`、`..`、路径分隔符、NUL 和控制字符。Windows 拒绝保留设备名、非法字符及尾部空格/点，不静默修剪或替换。
- 每次写操作核对当前空间、目录授权与版本、目标类型和根目录边界；创建允许位于授权根目录，重命名/删除不得针对根目录自身。
- 写操作不得通过符号链接、Windows junction（目录联接）或重解析点越界。第一版拒绝链接条目的修改，也不得沿链接目录创建子项；读取能力不扩大。
- 操作返回实际相对路径和明确结果，前端不得凭乐观推测宣告成功。

### 5.2 不覆盖、授权撤销与回收站

- 新建必须排他；重命名必须有“不替换已有目标”的语义，不能仅“检查目标不存在，再调用可能覆盖的重命名”。
- 对 Windows、macOS、Linux 分别做有明确结论的最小平台验证，检查授权撤销、链接替换、目标替换竞争。已有受限读写能力不证明已有安全的目录修改能力。
- 优先扩展现有受限平台接口，不另起通用文件系统框架；不得用命令拼接或绕过目录授权赶进度。无法可靠约束的操作拒绝执行，并记录限制。
- 回收站在主进程/平台适配层执行，服务端负责授权。一次路径解析并不能消除异步系统调用期间的目标替换风险，必须明确实际能力与限制。
- 不默认建设操作票据机制；只有现有跨层调用确有必要时才补最小受限桥接，票据本身不是操作系统原子保证。
- 回收站不可用、权限不足、占用等明确失败，永不调用永久删除作为备用实现。

### 5.3 三平台代码设计（本次确认）

统一调用链为：目录界面 → 授权文件服务 → `mutateBoundedEntry` 公共协议 → 当前平台原生后端。界面和服务不实现系统回收站，不把 NTFS、盘符或 Windows 回收站元数据格式当成通用条件。

- 公共协议统一承载创建、非覆盖重命名、移到回收站、明确失败和结果不确定；保留 prepare → 授权复核 → commit 流程。握手只是授权复核，不是操作系统原子保证。
- 原生层按平台隔离 Windows / macOS / Linux 实现，公用请求、结果和授权协议；不为了平台分层另建通用文件操作框架。
- Windows：受限句柄操作、排他创建、非覆盖重命名。当前回收站后端仅支持本地固定 NTFS 卷和已初始化用户回收站，这是该后端的限制，不是产品统一限制。
- macOS：使用受限目录描述符、禁止跟随链接的解析与平台非覆盖重命名能力；废纸篓遵循 macOS 用户/卷级语义。需验证路径型系统废纸篓 API 的替换竞争，不能仅用一次 realpath 校验后直接调用。
- Linux：使用受限目录描述符、禁止跟随链接的解析、排他创建及原子非覆盖重命名能力；回收站遵循 FreeDesktop Trash 规范，处理用户数据目录及卷级回收站、所有权、权限和同名冲突。
- Unix 的目录描述符不会像 Windows 共享模式那样自动阻止目录移动。必须专门验证准备后祖先/目标被移动、替换的场景；不得把持有描述符直接当成范围不可变保证。不满足约束时拒绝操作。
- 各平台名称规则由可信层决定；公共输入约束与平台约束分开。界面名称校验也必须接入平台能力，不能把 Windows 保留设备名规则硬套到其他平台。
- 后续通过授权目录的可信能力查询报告各操作是否可用及原因，界面不得只靠操作系统名称猜测；未实现的操作不提供可执行入口。能力查询不替代每次提交时的授权和文件系统检查。
- 回收站不可用或跨卷安全移动无法保证时明确失败，禁止永久删除兜底。网络卷、可移动卷、不同文件系统分别按真实能力判断，不承诺所有卷都支持。

**当前落地边界：** 公共调用入口已允许三平台原生助手，并按平台传递最小环境；Windows 原生后端已存在。macOS/Linux 原生创建、重命名和回收站后端，以及目录能力查询和界面平台名称策略仍待实现。非 Windows 当前继续安全返回 `unsupported`，不能将公共入口改造或模拟协议测试称为三平台功能完成。

**三平台验收要求：** 每个平台分别构建并运行创建/重命名/回收站恢复、同名竞争、链接及祖先替换、授权撤销测试；补充各自文件系统限制。Windows 上的通过记录不能替代 macOS/Linux 的实机结果。

## 7. 实施顺序与交付

1. **最小平台验证：** 分别明确 Windows、macOS、Linux 新建、非覆盖重命名、回收站的受限实现方式和风险；保持统一契约、独立适配和分平台验收。
2. **低风险闭环：** 菜单、路径复制、系统定位、名称框、新建与既有刷新。
3. **受限修改闭环：** 先关闭策略与必要入口保护、重命名、回收站确认、其他视图失效。

### Windows 重命名乱码修复

- 用户截图中的随机尾字符确实出现在磁盘文件名中，不是界面渲染或输入法问题。
- 原因：`rename_by_handle`（按文件句柄重命名的函数）为 `FILE_RENAME_INFO`（Windows 重命名参数）分配缓冲区时遗漏 UTF-16 字符串结束符。缓冲区刚好填满时，系统的路径转换可能继续读取末尾外的内存，追加随机字符。
- 修复：额外预留一个 UTF-16 零字符，保持名称长度字段不含结束符；沿用非覆盖重命名和受限句柄保护，不降级为不受限路径操作。回收站内部使用同一重命名函数，也获得修复。
- 单项原生回归测试 `rename_preserves_exact_unicode_names_at_every_buffer_alignment`（验证不同缓冲区对齐下名称完整性的测试）在修复前真实复现随机尾字符，修复后通过；覆盖中文、补充平面字符及八种名称长度，验证名称精确一致且文件内容不变。

## 14. Windows 回收站目录大小写修复与用户验收（2026-10-07）

### 修复

- 现象：D: 卷上「移到回收站」显示「当前平台或文件系统无法安全执行此操作，未修改文件」；同一卷的新建与重命名正常，C: 卷回收正常。
- 原因：原生修改后端用句柄规范路径与请求路径做逐字符（区分大小写）比较。D: 卷回收站根目录在磁盘上的存储名是全大写 `$RECYCLE.BIN`，代码硬编码 `$Recycle.Bin`；比较失败被 `recycle.rs` 一律改写为 `unsupported`，界面据此显示「平台或文件系统无法安全执行」。NTFS 不区分大小写但保留创建时的大小写，资源管理器因此不受影响（详见 `docs/bugs/bug-20261007-windows-recycle-bin-case-mismatch.md`）。
- 修复：`windows.rs` 新增 `same_path`（仅折叠 ASCII 大小写），替换源路径校验与 `pin_directory` 两处比较。句柄仍由被比较的请求字符串打开、准备阶段仍拒绝重解析点、`path.starts_with(root)` 的词法包含判断仍区分大小写，因此不降低防路径替换能力；非 ASCII 大小写差异仍失败关闭。
