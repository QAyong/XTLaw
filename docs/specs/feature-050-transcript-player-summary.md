# Feature-050：播放器智能纪要

**日期：** 2026-11-09
**状态：** 草案，待确认（2026-11-09 起草；未实现、未运行）
**范围：** 只改 `plugins/transcript-player/`。宿主提交能力见 [Feature-049](feature-049-plugin-composer-submit.md)。播放、文字记录、搜索和引用定位仍以 [Feature-048](feature-048-transcript-player-plugin.md) 已完成的 `0.2.6` 为准，不重做。
**承接：** Feature-048、Feature-049。没有 Feature-049 时，本规格不能上线，只能提示升级宿主。

## 文件与术语说明

| 原名称 | 中文含义 | 用途 |
| --- | --- | --- |
| `sourceId` | 媒体来源标识 | 同一个音视频跨句柄保持稳定；纪要按它归档 |
| `contentHash` | 字幕内容指纹 | 由当前句子文本算出；字幕一改就作废旧纪要 |
| `composerSubmits` | 可提交消息声明 | 播放器只声明一句固定请求，运行时不改字 |
| `write-summary` | 写入纪要工具 | 当前 Agent 写完后调用，把正文交回播放器 |
| `views.broadcast` | 视图广播 | 通知已经打开的播放器刷新纪要 |
| `context.storage` | 插件私有存储 | 整包最多 256 KiB；只存纪要和指纹，不存整份字幕 |

## 1. 背景

播放器右侧已经有「智能纪要」页，现在是空占位，写着以后由 Agent 根据文字记录生成。Feature-048 的播放和文字记录需求已经完成，这一页是下一件事。

纪要要由正在聊天的 Agent 写，再回到这个页签。播放器不自己调用模型，也不把提示塞进草稿等用户再点发送。用户点一次「让 Agent 写纪要」，宿主按 Feature-049 提交一条看得见的消息；Agent 写完后调用播放器的写入工具，页签才出现内容。

## 2. 已定

1. **生成者是当前聊天里的 Agent。** 不使用插件内部的 `models.generateText`，也不附带 Skill 来偷偷生成。
2. **点击后走 Feature-049。** 不把请求插入草稿，不模拟点击发送。
3. **没有字幕就不能写。** 不编造文字稿，也不在打开视频时自动生成。
4. **纪要属于「这个媒体 + 这份字幕」。** 换字幕或字幕内容变了，旧纪要不继续显示。
5. **不写回音视频原件。** 不加 `selectedResourceWrite`。
6. **超限就整次失败。** 不截断文字稿，也不截断纪要后假装完整。

## 3. 目标与非目标

**目标**

- 有字幕时，纪要页提供「让 Agent 写纪要」。
- 点击后向用户选定的聊天提交固定请求，并附上当前文字稿引用。
- Agent 通过写入工具交回纪要；已打开的播放器立即显示，关掉再打开仍在。
- 字幕变化后回到「还没有纪要」，不把旧文当成新稿的纪要。

**非目标**

- 不实现 Feature-049 的宿主能力。宿主没有 `context.composer.submit` 时，按钮提示升级，不另做一套代发。
- 不做自动生成、说话人分离、纪要里的时间戳跳转、纪要编辑器。
- 不把整份字幕放进插件存储。存储只留纪要正文、媒体标识、字幕资源 ID 和内容指纹。
- 不改 ArtPlayer，不改文字记录、搜索、引用和定位。
- 不在本规格里向上游提 PR。

## 4. 用户看见什么

| 状态 | 纪要页 |
| --- | --- |
| 还没加载字幕 | 「还没有文字稿。」按钮不可用 |
| 已有字幕，还没纪要 | 「还没有纪要。」按钮为「让 Agent 写纪要」 |
| 正在提交 | 按钮不可用，提示「正在发送到聊天…」 |
| 已提交，Agent 还没交回 | 保持原内容。首次是空状态，重写时保留上一份，直到新的一份通过校验 |
| 已交回，且正在看纪要页 | 直接换成新正文 |
| 已交回，但正在看文字记录 | 不强制切页。纪要页签上出现小点，打开后消失 |
| 字幕换了或内容变了 | 清空当前显示，回到「还没有纪要」 |
| 宿主太旧或未授权 | 按钮不可用，分别提示升级宿主或重新确认插件授权 |

多个聊天时，沿用现在引用菜单的选择方式。只有一个聊天时直接提交。没有聊天时提示先打开聊天输入框。

正文按纯文本显示，保留换行。不把 Agent 交回的内容当 HTML 渲染，不执行链接。

## 5. 提交给 Agent

播放器声明一条 Feature-049 消息，标题「写智能纪要」，正文固定为：

> 请根据引用的文字记录写智能纪要，并写回播放器。

运行时不能改这句，也不能另附隐藏指令。

点击按钮时：

1. 视图同步调用 `context.composer.arm()`。
2. 用 `listTargets()` 选择聊天。多个目标时等用户选完；凭证过期就要求再点一次。
3. 把当前已加载句子的纯文本作为一条引用附上。文本包含时间范围和句子原文，不编造说话人。
4. 调用 `context.composer.submit`。成功后只提示已发送到哪个聊天，不在本地预写纪要。

引用沿用宿主的引用上限，不沿用选区引用的 32768 个 UTF-16 字符限制。整份文字稿仍可能超过宿主上限。超过时不提交，提示文字稿太长，不能整份交给 Agent。不截断，也不改成只引用开头。

这一期不另做「分页读取文字稿」工具。长文字稿要等以后的规格，不能在这一期偷偷读文件绕过上限。

## 6. 写回

播放器新增 `permissions.agent`，并注册一个 `access: "write"` 工具，ID 为 `<plugin-id>.write-summary`。参数是封闭对象：

| 字段 | 含义 |
| --- | --- |
| `mediaKey` | 媒体 `sourceId` |
| `subtitleId` | 当前字幕资源 ID |
| `contentHash` | 提交时看到的字幕内容指纹 |
| `text` | 纪要正文，1–32768 个字符 |

三个标识都必须对上插件记录的「当前字幕」。对不上就拒绝，不覆盖旧纪要。工具不接受任意文件路径，也不读取别的插件存储。

字幕加载成功后，视图计算指纹，连同 `mediaKey` 和 `subtitleId` 交给现有宿主命令保存。写入工具只相信这份记录，不相信调用方自己声称「这就是当前字幕」。

保存时必须和现有字幕记忆放在同一次 `storage.set` 里。现在的存储结构是 `{ subtitles: { [mediaKey]: 字幕选择 } }`。新增纪要时保留 `subtitles`，不能只写纪要把字幕记忆冲掉。

指纹用规范化后的句子文本计算：按句序拼接 `start`、`end` 和 `text`，空白差异算不同内容。只改显示、不改句子，不算新字幕。

存储整包上限 256 KiB。纪要正文加上现有字幕记忆后放不下时，写入失败并让工具返回明确错误。不删除其他视频的字幕记忆来腾地方。最多保留 20 份纪要；超过时删掉最久没有更新的，且不删当前这份。

写入成功后 `views.broadcast`。广播只带媒体标识、字幕 ID、指纹和正文。每个打开的播放器只接收自己的媒体和当前指纹；对不上就忽略。新打开的视图不依赖广播，打开时用隐藏命令读取已保存的纪要。

## 7. 权限与版本

在 `0.2.6` 已有权限上增加：

| 权限 | 原因 |
| --- | --- |
| `composerSubmit` | 用户点击后提交固定消息 |
| `agent` | 让当前 Agent 调用写入工具 |

不增加 `models`、`selectedResourceWrite`、`taskMessages`。

`engines.lexora` 的下限改为第一个同时提供 Feature-049 和本插件所用 Agent 工具的应用版本。在那个版本之前，按钮保持不可用。升级插件时，安装确认页会把这两项标为新权限；用户拒绝后，播放和文字记录仍可用，只是不能写纪要。

实现时把插件版本从 `0.2.6` 递增。本规格不预写版本号。

## 8. 风险

- **文字稿太长。** 这一期宁可失败，也不截断后让 Agent 根据半份稿写纪要。
- **存储被字幕记忆和纪要共用。** 写入必须合并，不能覆盖 `{ subtitles }`。
- **多个页签同时开着同一视频。** 以最后一次成功加载的字幕指纹为准；旧页签收到对不上的广播时不改自己的画面。
- **Agent 可能不调用写入工具。** 页签保持等待前的内容。播放器不设超时，也不自己补一份纪要。
- **重写。** 再点一次只是再提交一条消息。新纪要通过校验前，旧纪要继续显示。

## 9. 验证

- 单元测试：指纹随句子变化；存储合并不丢失字幕记忆；写入工具拒绝过期指纹；超限不截断；广播只更新匹配的媒体。
- 类型检查和插件现有测试。
- Windows 宿主实机未跑之前，不写成已验收。实机至少看：唯一聊天时一点即发送；多个聊天必须选择；Agent 交回后纪要页出现正文；换字幕后旧纪要消失。
