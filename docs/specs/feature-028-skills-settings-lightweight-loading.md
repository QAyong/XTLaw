# 规格 028：Skills 设置列表轻量加载

**日期：** 2026-10-09
**状态：** 已实现，待上游 CI 与人工验证。

**目标：** 打开 Skills 设置不再完整读取所有技能包，消除首次打开长时间等待。保留现有安装、更新、使用流程及安全边界。

## 1. 一句话结论

打开 Skills 设置是在看技能目录，不应该因此读取并哈希所有技能包里的附件。

设置列表、启用/禁用、删除、详情改为只读各个 `SKILL.md`（轻量发现）。完整包读取与校验只保留在确实需要的流程：安装/更新预览，以及用户手动选择某个技能。同时对完整读取加入有上限的并发，降低这些流程的等待。

## 2. 实测结论（本机，16 个有效技能，约 1100 个文件、22 MB）

测量对象是 `SkillService.list()`，使用真实的 `~/.xtlaw/buddy/agent/skills`，内存数据库，目录只读。

| 路径 | 首次 | 重复 |
| --- | --- | --- |
| 完整加载（改前） | 50.4 秒 | 约 200 毫秒 |
| 轻量加载 | 0.85 秒 | 约 35 毫秒 |
| 完整加载（并发 10 后） | 9.5 秒 | 约 220–290 毫秒 |

单个技能包完整读取（缓存已热，串行）：`lark`（416 文件，5 MB）18.2 秒；`html-ppt-skill` 9.9 秒；`impeccable` 7.0 秒；`contract-copilot` 5.3 秒。每个文件约 44 毫秒，与文件大小无关。

**根因：** `readBoundedFile` 每读一个文件就通过 `execFile` 启动一次原生读取器子进程（`platform/filesystem/nativeBoundedFile.ts`）。同一批文件用普通 `fs.readFile` 并发读取仅需约 50 毫秒。原生读取器负责防符号链接逃逸和读取期间被替换（持有根目录句柄、按句柄反查最终路径），不能用 Node `fs` 直接替代。

并发读取 `lark`：并发 1 为 18.9 秒，4 为 3.7 秒，8 为 3.1 秒，16 为 3.0 秒，从 8 起进入平台期。

以上是单机单次结果，不是基准套件；完整加载的测量顺序在轻量之前，系统文件缓存可能略有利于后者。

## 3. 代码行为（改前）

- `useSkillsManager.load()` 调用 `api.list(spaceId)`，未传 `metadataOnly`，默认走完整加载。
- 完整加载的 `SkillPackageCache.load()` 先调用 `inspectPackage()` 递归枚举包内目录，缓存未命中时 `readSkill()` 读取包内全部文件并计算完整包哈希。
- `SkillService.#list()` 每次先失效目录解析缓存；完整结果不写入解析缓存。
- `setEnabled`、`remove`、详情内部也会触发完整解析，所以只改列表请求会把等待转移到第一次点击上。
- 前端忽略 `discovery` 类型目录事件，不忽略 `management` 类型。轻量解析发出 `discovery` 事件，且不执行“新发现技能登记”，也就不再触发该自我刷新。

## 4. 实现

### 4.1 列表与管理操作

- `useSkillsManager.ts`：设置列表请求改为 `api.list(spaceId, true)`。
- `SkillService.ts`：
  - `setEnabled`、`remove` 通过轻量解析确认当前技能，返回的列表也使用轻量结果，避免版本格式在轻量与完整之间来回切换。
  - 新增 `isCurrentRevision`：传入版本等于 `SKILL.md` 版本或完整包版本都视为当前版本，与 `materializeForSpace` 一致。
  - `#currentSkill` 在两种情况下回退到一次完整解析：该技能尚无安装记录（完整解析负责登记）；传入版本与轻量版本都不匹配（调用方持有完整包版本，保留整包一致性检查）。
  - `install` 最终返回的列表改为轻量；安装与更新的预览仍使用完整列表。
- `SkillInspector.ts`：详情目标在列表中存在但尚无安装记录时触发一次刷新登记，避免“列表可见但详情找不到”。
- `useDesktopWorkbench.ts`：`startTaskWithSkill`（“创建插件”入口）改为 `skills.list(null, true)`，不再整库完整读取。

### 4.2 完整读取并发

`skillFiles.ts` 的 `readSkillFiles` 改为：先同步遍历并完成大小、文件数、符号链接检查，再以最多 10 个并发调用原有的 `readBoundedFile`。任一读取失败后不再启动新的读取。结果按遍历顺序组装；包哈希按文件名排序，因此版本号不变。每个文件仍走同一个有边界的读取，安全检查不变。

## 5. 使用场景：谁会读取完整技能包

| 场景 | 范围 |
| --- | --- |
| 用户手动选择某个技能并发送（`materializeForSpace`） | 仅被选中的包；每个技能每次启动后首次 |
| 安装或更新预览 | 导入源，加已安装技能库的完整列表 |
| 新发现技能首次启用或查看详情 | 整个技能库一次（完整解析登记记录） |

不读取完整包：打开设置页、输入框 `/` 技能选择（本来就是轻量）、普通消息发送与会话启动、AI 自行发现并用文件工具读取技能附件（走 AI 自己的读取路径与 `skillReadRoots`，与本流程无关）。

## 6. 已知行为变化与限制

- 附件有问题（符号链接、超大、文件过多）的技能，列表中不再标为“无效”，使用时才报错。已安装技能安装时已校验，风险较小；工作区 `.agents/skills` 下的目录型技能没有安装校验，影响更明显。
- 安装/更新预览仍会完整读取已安装技能库，应用启动后首次安装预览会承担原先打开设置页时的等待（并发后约 9.5 秒量级）。
- 大包（`lark` 等 130 文件以上）首次被手动选择时约 3 秒（并发 10），改前约 18 秒。
- 轻量解析会更新会话资源快照，可能额外发出一次 `resources` 事件，前端会多刷新一次列表；每次约 35 毫秒，仅在变化时发生。

## 7. 未做与后续

- **批量原生读取（第 3 步）：** 在 Rust 读取器增加批量请求，一个技能包只启动一个进程，预计可把大包读取降到 0.2 秒量级（推算，未测）。需要改三个平台的原生实现与安全边界，且使用场景很窄，暂不做。如经常手动选择大包再单独立项。
- 安装预览中的整库扫描，仅在“更新已装技能”时才需要比较版本，可单独评估是否避免。
- 设置页先显示旧数据再后台刷新、合并并发 `load()`：首次打开已低于 1 秒，之后为毫秒级，暂不需要。
- 不改变安装、更新时的文件边界与包校验流程；不改变模型发现、读取技能的现有行为；不引入全局 KeepAlive、跨页面持久化缓存或文件系统监听；不改数据库迁移、依赖、品牌或打包配置。

## 9. 与现有规格的关系

规格 004（`feature-004-skill-lazy-loading.md`）第 67 行“打开技能目录列表时也执行完整刷新”描述的是旧行为。本规格将设置列表改为轻量发现，该句不再成立；规格 004 的其余内容（消息发送与会话准备不扫描全库）不受影响。
