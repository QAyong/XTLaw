### 使用场景与问题 / Use case and problem

**场景：让 AI 处理一大批数据，但不想让主 AI 亲自处理。** 例如我手上有几千条 JSON，要做清洗：统一名称写法、从文本里抽字段、分类、去重。这类活不需要强模型，也不需要多步推理和调用工具，一个便宜的小模型加一段提示词就够。

现在的做法有两种，都不理想：

- 让主 AI 自己读数据、自己改。数据全进了主对话的上下文，贵、慢，上下文还会被撑满。
- 委派给子代理（`lexora_agents`）。子代理是完整的 agent：有自己的 `runId`、工具、权限、审核流程，用来跑一次“把这一条改一下”太重，而且每个子代理仍然是对话式的 agent 循环。

我想要的是介于两者之间的东西：**一次无状态的 AI 处理**。给它一段提示词和输入，它调用一个模型，返回结果。它没有会话上下文，没有工具，也不是一个 agent。

**不限于文字。** 同样的需求也出现在别的模态上：

- 图片：几百张票据或截图，批量抽取文字或字段。
- 语音：一批录音，批量转写后再整理。
- 文本：上面说的 JSON 清洗、分类、抽取、翻译。

**最关键的一点：用哪个模型，要跟随设置里已有的配置**，而不是工具自己另配一套。

### 期望的体验 / Desired outcome

1. 主 AI 有一个轻量的“AI 处理”能力：传入提示词和输入（文本、文件，或图片、音频），得到结果。它不是子代理，没有自己的会话、工具和审核流程。
2. **模型选择沿用设置。** 文本用设置里启用的聊天模型，图片沿用“图片”设置里已有的策略（自动/指定模型/原生，以及备用模型），语音沿用设置里的转写模型。用户在设置里配的便宜模型，这个能力就用它；不应该偷偷换成别的服务商。数据发往哪个服务商，受用户已有的配置和授权约束。
3. 输入输出尽量不经过主对话上下文：大批量数据从文件读、结果写回文件，主 AI 只看到“处理了多少条、失败了多少条”。
4. 输出可以要求结构化（例如 JSON 结构），不符合的结果能被识别并单独重试或标记，不要整批静默失败。
5. 批量处理前，最好能先对少量样本试跑，让用户或主 AI 确认效果再放量。

### 当前做法或替代方案 / Current workaround or alternatives

- 让主 AI 自己处理，或写脚本调用外部接口。前者贵且占上下文，后者要自己管密钥，也绕过了设置里的模型配置和授权。
- 用子代理，能做但太重，且和“一次模型调用”的预期不符。

### 补充材料 / Additional context

读代码时看到的相关现状，供维护者参考，不是实现要求：

- 设置里已有按模态区分的模型配置：图片有 `understand` / `extract` / `document` / `generate` / `edit` 各自的 `mode` + 目标模型 + 备用模型；模型有 `chat` / `transcription` / `speech` 类型。新能力可以复用这些，而不是新增一套。
- 已有 `codemode`，可以用脚本编排工具。如果这个能力能在 codemode 里被调用，主 AI 就可以自己写“分块、并发调用、校验、写回”的循环，工具本身只需要把“一次调用”做好；批量调度是否做成专门工具，可以等真实用法出来再定。
- 社区里类似的方向有 DocETL、LOTUS 这类用 LLM 做 map/filter/extract 算子的数据处理框架，以及各家的批处理接口；MCP 的 sampling 也是“工具内嵌一次模型调用”的思路。

**没有验证的地方**

- 没有评估过各服务商对批量请求的限速和计费差异。
- 小模型在具体清洗任务上的准确率没有测过，所以才需要上面的结构化校验和样本试跑。

如果维护者觉得方向合适但范围太大，我可以先拆成“只支持文本、模型沿用聊天设置”的第一步。
