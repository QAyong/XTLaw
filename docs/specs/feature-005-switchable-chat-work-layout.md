# 方案 005：聊天窗口与工作区位置切换

**日期：** 2026-09-23<br>
**状态：** 实现中；布局、提示、输入区适配及针对性尺寸检查已更新，仍需开发预览验收<br>
**范围：** 前端布局与交互

## 1. 使用场景与目标

法律工作者阅读或修改 Word/PDF 合同时，需要把合同放在中间，获得更宽的工作空间，同时在右侧随时向聊天窗口提问，输入框保持可用。

本方案只调整聊天窗口和工作区的位置、宽度及控制方式，不改变文档编辑能力，也不改变两个区域中的内容。

## 2. 当前界面与相关代码

| 区域或文件 | 当前行为 | 本需求的影响 |
| --- | --- | --- |
| `AppShell.tsx` | 按左侧栏、聊天窗口、工作区的顺序组成主界面 | 切换时需要同步改变两个区域的位置和键盘焦点顺序，保留各自状态 |
| `WorkPanel.tsx` | 包含工作区标签、最大化按钮和左边界拖动条 | 工作区居中后，拖动条需要位于其右边界 |
| `useAppShellRuntime.tsx` | 管理工作区展示、侧边栏收起及最大化 | 右上角收起按钮要随布局控制当前右侧区域 |
| `work-panel-resize.ts`、`sidebar-resize.ts` | 现有宽度计算优先保障中间聊天窗口的 450px 最小宽度 | 切换后需要按“中间工作区、右侧聊天窗口”重新计算，不能只交换视觉顺序 |
| `chrome.css`、`work-panel.css` | 顶栏右侧保留面板按钮和系统窗口按钮的位置 | 聊天窗口移到右侧后，标题栏仍须为这些按钮留出空间 |
| `PluginViewTab.tsx` | 工作区内插件视图根据测得的位置更新原生视图边界 | 即使大小不变，仅位置变化也必须同步原生视图边界 |

现有 `Cmd/Ctrl+J` 用于打开或收起工作区，`Cmd/Ctrl+B` 用于收起或展开左侧栏。本方案保留这两个快捷键原有的含义。

## 3. 两种布局

```text
默认布局： [左侧栏] [聊天窗口：弹性占据中间] [工作区：右侧]
工作布局： [左侧栏] [工作区：弹性占据中间] [聊天窗口：右侧]
```

- 首次使用或未保存设置时，保持现有默认布局。
- 工作布局把合同所在的工作区放在中间，并优先给它剩余宽度。右侧聊天窗口默认宽度和最小宽度均为 450px，与默认布局一致；只要聊天窗口可见，输入框就必须能使用。
- 左侧栏始终在左侧。它的收起、重新展开、边界拖动和 `Cmd/Ctrl+B` 逻辑都保持原样。左侧栏收起后，重新展开按钮仍位于当前**中间区域**标题栏的左边，不随聊天窗口移到右侧。
- 用户选择的布局作为应用级偏好保存，跨会话和应用重启生效。两种布局分别记住各自的右侧区域目标宽度。窗口暂时变窄时，实际显示宽度可以被压缩，但不能覆盖用户保存的目标宽度。
- 工作区尚未打开或已关闭时，聊天窗口填满左侧栏以外的空间。再次打开工作区时，恢复用户保存的布局，不出现空白中间列。
- 设置等其他页面沿用其现有布局；回到聊天页面时再应用这一偏好。

## 4. 标题栏与按钮位置

沿用现有标题栏高度、按钮尺寸、悬停和焦点样式以及主题色，不新增一整条工具栏。

两个区域都展开时，标题栏的主要元素如下：

```text
默认布局：
[左侧栏] [聊天标题 | 新建任务 | 搜索] [工作区标签 | + | 最大化] [切换] [收起工作区] [窗口按钮]

工作布局：
[左侧栏] [工作区标签 | + | 最大化] [聊天标题 | 新建任务 | 搜索] [切换] [收起聊天] [窗口按钮]
```

右侧区域收起后：

```text
[左侧栏] [中间区域标题栏，填满剩余空间] [展开右侧区域] [窗口按钮]
```

- **切换按钮**紧挨着右上角现有的收起按钮。只有聊天窗口和工作区**都已展开**时才显示；点击后立即互换位置，无须先收起。
- 右上角固定位置的按钮始终控制**当前右侧区域**：默认布局控制工作区，工作布局控制聊天窗口。提示文字和辅助功能名称应准确说明“收起聊天”“展开工作区”等当前动作。
- **最大化／还原按钮**留在工作区自己的标题栏，不与切换按钮或右上角收起按钮混用。工作区标签和 `+` 按钮也始终留在工作区标题栏。
- 聊天标题、“新建任务”和“搜索”跟随聊天窗口移动。聊天窗口在右侧时，长标题可省略显示，但操作按钮及右上角固定按钮必须可点击。
- Windows/Linux 的窗口按钮仍位于整个窗口最右端，背景与右侧区域协调；macOS 左侧系统按钮保留安全空间。标题栏可拖动区域不得覆盖任何按钮。

## 5. 各状态下的交互

| 状态 | 右上角固定按钮 | 切换按钮 | 工作区最大化按钮 |
| --- | --- | --- | --- |
| 默认布局，两个区域展开 | 收起工作区 | 显示，点击切到工作布局 | 位于工作区标题栏，可用 |
| 默认布局，工作区收起 | 展开工作区 | 隐藏 | 工作区标题栏不可见 |
| 工作布局，两个区域展开 | 收起聊天窗口 | 显示，点击切回默认布局 | 位于工作区标题栏，可用 |
| 工作布局，聊天窗口收起 | 展开聊天窗口 | 隐藏 | 工作区已占满可用宽度，无额外最大化动作 |
| 任一布局下工作区最大化 | 按下文处理 | 隐藏，直到还原 | 显示“还原”，还原至之前的布局和宽度 |
| 当前会话未打开工作区 | 打开工作区 | 隐藏 | 工作区标题栏不可见 |

最大化是临时展示状态：工作区占据左侧栏以外的空间，聊天窗口暂时隐藏；还原后回到最大化前的布局、区域可见性和宽度，不修改保存的布局偏好。工作布局下，右上角按钮可以重新展开隐藏的聊天窗口；默认布局下，保留现有的“收起最大化工作区”能力。若聊天窗口已收起，工作区本来就占满空间，最大化按钮可禁用或不显示，实施时保持交互含义明确。

右上角按钮在工作布局下控制聊天窗口，但 `Cmd/Ctrl+J` **仍然控制工作区**，以免改变现有快捷键习惯。若通过快捷键收起工作区，聊天窗口填满剩余空间；再次打开工作区后恢复工作布局。右上角按钮控制聊天窗口时，提示文字不能错误地标注 `Cmd/Ctrl+J`。

## 6. 边界拖动与窄窗口适配

- 两个区域都显示时，它们的公共边界可以用鼠标拖动，也可以用键盘调整。默认布局中，向左拖动会加宽右侧工作区；工作布局中，向右拖动会加宽中间工作区，向左拖动会加宽右侧聊天窗口。
- 拖动条的可见位置、鼠标可点击范围、键盘左右方向、辅助功能数值以及双击重置都要跟随实际区域顺序。取消拖动时恢复拖动前的宽度。任一区域收起或工作区最大化时，不显示公共边界拖动条。
- 工作布局在窗口变窄时优先保障中间工作区，同时确保右侧聊天输入框仍可用。与目前保护中间聊天窗口的方式一致，必要时先让左侧栏收起。
- 用户手动重新展开左侧栏后，不能立刻又被自动收起。可以压缩右侧聊天窗口并启用紧凑输入框布局，同时限制侧边栏当前宽度。
- 两种布局统一采用 450px 聊天最小宽度，中间工作区最小宽度为 300px。应用支持的最小窗口宽度为 1040px；空间不足时优先收起侧边栏，并保留两个区域的最小宽度。
- 拖动窗口边缘导致的临时宽度限制不覆盖用户保存的目标宽度。窗口重新变宽后，恢复用户之前调整的比例。

## 7. 状态、焦点与原生视图

- 切换位置时保留当前工作区标签、文档编辑状态、浏览器或插件视图、聊天记录滚动位置以及未发送的输入内容；尽可能保留当前焦点。不能为了换位置而销毁并重新创建两个区域。
- 键盘 Tab 焦点顺序应与屏幕上看到的左右顺序一致；只靠 CSS 调整视觉顺序、却保留旧焦点顺序不可接受。
- 工作区标签及其打开状态仍归当前会话管理；全局布局偏好不能使一个会话的文档出现在另一会话中。
- 插件等原生视图在位置变化时必须收到新的边界坐标，包括宽高未变化的移动。遮罩、收起和最大化期间也要正确隐藏或覆盖这些视图。
- AI 回合处理标题下方显示的等待模型响应状态，其标题左边缘与上方处理标题对齐；展开的详细活动内容继续保留层级缩进。
- 页面重载、切换会话、工作区关闭再打开、左侧栏收起再展开、最大化再还原，以及调整窗口大小后，不能残留错误的拖动条位置、原生视图边界、提示文字或焦点位置。
- 所有新增的按钮文字、提示和辅助功能名称都要通过现有多语言系统提供，准确描述当前动作。

## 8. 建议实施顺序

1. 先建立识别两种布局的宽度计算和拖动方向，并做针对性测试；把现有默认布局计算作为基线。
2. 增加持久化的布局偏好，以及两种布局各自的右侧区域目标宽度。区分“右侧区域当前是否显示”和“当前会话是否打开工作区”。
3. 一起调整两个区域的页面顺序及标题栏按钮预留位置，保持组件状态，修正左侧栏重新展开按钮的位置，并保留各平台窗口拖动和安全区域。
4. 让原生视图响应只有位置变化的移动，并使键盘焦点顺序与视觉顺序一致。
5. 补全多语言文字，并在实现时同步更新仓库的 UX 规范和相关 E2E 场景文档；按照仓库对分支 ADR 的规则处理 ADR 0238 中原有的宽度优先级约定。

以上是实施计划，不代表功能已经完成。

## 9. 验收条件

- [ ] 没有保存过布局偏好的用户，看到的默认界面与现有行为一致。
- [ ] 两个区域都展开时，切换按钮出现在右上角收起按钮旁，点击后立即交换中间和右侧位置。
- [ ] 右侧区域收起时，切换按钮隐藏；右上角按钮展开同一个区域。工作布局下，该按钮控制聊天窗口。
- [ ] 左侧栏的按钮、位置和收起／展开逻辑在两种布局下均保持一致。
- [ ] 打开合同后切换布局、拖动边界、继续输入未发送的聊天内容，合同和聊天状态均保留。
- [ ] 鼠标拖动方向、键盘调整、取消拖动、双击重置均符合实际边界；重启应用或窗口临时变窄后，保存的宽度能够恢复。
- [ ] 两种布局下工作区都能最大化、还原，且还原后回到原来的布局，不改写保存的偏好。
- [ ] 在应用支持的最小窗口尺寸下，两个可见区域仍可操作；手动展开左侧栏不会出现反复收起、展开。
- [ ] Windows/Linux 窗口按钮、macOS 系统按钮、插件原生视图、长标签名称，以及明暗主题的位置和显示均正确。
- [ ] 组件或服务层测试覆盖一条真实操作路径：打开合同、切到工作布局、拖动边界、继续提问、收起再展开聊天、最大化再还原、切回默认布局。除非用户明确要求，不运行 `test:e2e:*`。

## 10. 待实施时确认的细节

两种布局下聊天窗口的最小宽度统一为 450px。最终验收以输入、发送、模型选择等必要操作没有横向裁切且可正常使用为准。
