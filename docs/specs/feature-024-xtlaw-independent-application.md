# Spec-024：XTLaw 独立应用隔离方案

**日期：** 2026-10-07

**状态：** 本轮开发版交付已由用户于 2026-10-07 明确确认验收通过，包含开发预览、Office 预装市场展示及官方署名；检查与交接见第 12–15 节。发行级安装、并行运行、升级卸载、Windows ACL 与跨平台实测仍保留待验证状态。

**目标：** Lexora 与 XTLaw 是两个可同时安装、同时运行、独立更新和卸载的应用。

**数据策略：** 当前只有用户本人使用；不写自动导入逻辑，旧数据保留，以后按需手动迁移。

## 1. 背景与商业判断

XTLaw 是基于 Lexora 的二次开发产品。已有品牌替换和聊天欢迎页改造，但对外名称不同不代表数据、进程和系统资源已经独立。

当前没有其他用户，不需要为了存量用户投入自动迁移、迁移向导、Lexora 覆盖升级或旧品牌兼容安装器。应先把两个产品的边界做正确，避免将共享数据和系统服务的问题带到后续发布。

选择：**产品身份与运行资源独立，内部源码名称按需保留。**

- 不是只换名称和图标、继续共用数据的“换牌方案”。
- 不是把所有 `Lexora` 字符串全面改为 `XTLaw` 的大范围重构。
- 安装、数据、凭据、进程通信、服务和更新入口必须隔离。
- 类型、函数、工作区包名等不造成资源冲突的内部名称可以保留，降低改造成本和上游同步成本。
- 独立性是商业发布基础，不等于产品差异化完成；法律场景、默认技能、首次引导和工作流另行立项。

## 3. 需求边界

### 3.1 包含

1. XTLaw 独立安装身份、运行身份、数据、凭据和浏览器存储。
2. 正式版、开发版、测试版各自的路径与通信身份规则。
3. 原生组件和子进程使用一致的 XTLaw 路径配置。
4. Windows 沙盒服务、管道、权限资源和安装卸载逻辑隔离。
5. 自启动、快捷方式、通知身份、单实例锁，以及实际存在的系统注册项核查。
6. XTLaw 独立更新来源；安装与卸载不破坏 Lexora。
7. 助手负责代码核查、定向测试和构建；用户负责 Windows 安装和双应用真实验收。

### 3.2 不包含

- 自动扫描、导入、移动、删除或修改 `.lexora` 数据。
- 自动迁移向导、后台搬迁、首次启动兼容读取。
- 用 XTLaw 安装包替换或卸载 Lexora。
- 全量重命名内部类型、函数、Rust 包、原生二进制和工作区包名。
- 产品功能重设计、法律垂直内容、云端账号与商业计费系统。
- 助手未经另行授权启动开发预览，或代替用户执行发行级安装、升级、卸载及本机沙盒服务、防火墙操作。
- 未经另行要求生成安装包、提交、推送或更改 Git 历史。

## 4. 身份与数据设计

下表是**目标值**，不是已经实现的状态。默认路径不得借用 Lexora 的目录。

| 维度 | 正式版 | 开发版 | 测试版 |
| --- | --- | --- | --- |
| 显示名 | `XTLaw` | `XTLaw Dev` | `XTLaw Test` |
| 桌面应用标识 | `io.github.qayong.XTLaw` | `io.github.qayong.XTLaw.Development` | `io.github.qayong.XTLaw.Test` |
| 主数据目录 | `~/.xtlaw` | `~/.xtlaw-dev` | 显式指定的隔离临时目录 |
| 运行命名空间 | `xtlaw` | `xtlaw-dev` | `xtlaw-test` |
| Windows Electron 数据目录 | `%APPDATA%/XTLaw` | `%APPDATA%/XTLaw Dev` | 测试临时目录中的独立子目录 |
| Windows 状态与缓存根目录 | `%LOCALAPPDATA%/XTLaw` | `%LOCALAPPDATA%/XTLaw Dev` | 测试临时目录中的独立子目录 |

说明：`~` 表示用户主目录；`%APPDATA%` 与 `%LOCALAPPDATA%` 分别为 Windows 的漫游与本地应用数据目录。

### 4.1 路径规则

- 配置、会话、设置、授权记录、插件及技能安装数据进入 XTLaw 自己的主数据目录。
- Electron 的 `userData`（应用与浏览器存储目录）、`sessionData`（会话存储目录）、缓存、窗口状态、日志和崩溃文件分别核对，不依赖改显示名后自动正确。
- 凭据文件及系统凭据存储如存在应用级标识，均使用 XTLaw 身份；不自动读取 Lexora 凭据作兜底。
- Linux 和 macOS 使用各平台正常目录规范，但应用专属目录和通信路径使用 XTLaw 命名空间。
- 测试配置必须提供独立根目录；保留并扩展真实路径重叠保护，防止测试写入两个产品的正式或开发数据。
- 用户主动选择同一个工作目录、访问同一份业务文件不属于隔离失败；不得自动搬迁这些业务文件。

### 4.2 环境变量与子进程

环境变量可改变数据落点，是隔离边界，不只是内部名称。

本次采用 `XTLAW_HOME`（指定 XTLaw 主数据目录）和 `XTLAW_BUDDY_PROFILE`（选择运行档位）。现有 `LEXORA_HOME`、`LEXORA_BUDDY_PROFILE` 不作为 XTLaw 顶层启动的隐式回退，避免继承开发环境后重新读写旧数据。桌宠资源覆盖使用 `XTLAW_BUDDY_PET_SOCKET`、`XTLAW_BUDDY_PET_STATE_PATH`、`XTLAW_BUDDY_PET_PATH`；启动脚本已同步。

桌宠的数据、socket 和位置状态已使用上述 XTLaw 环境变量，父进程显式传入解析后的路径，不依赖继承的旧资源变量。本地 Agent 服务继续保留 `LEXORA_BUDDY_HOME`、`PI_CODING_AGENT_DIR` 等内部接口，但由父进程显式赋值为 XTLaw 的目录；不得将继承的旧路径原样透传。插件开发和测试脚本也已同步。

显式目录覆盖需校验绝对路径和已知保护目录重叠；拒绝指向 Lexora 的默认数据根目录。此保护不是对任意自定义旧目录的自动发现承诺。

### 4.3 原生组件与进程通信

- Rust 桌宠必须读取 XTLaw 配置，不得独立兜底到 `~/.lexora/config.toml`。
- 浏览器适配器、桌宠、其他原生宿主的 socket（本机进程通信端点）、Windows 命名管道和状态文件使用 XTLaw 身份。
- 核查单实例锁、互斥量和固定端口；发现固定端口冲突时采用独立或动态分配，不凭空新增通信机制。
- 允许同时运行 Lexora 和 XTLaw；每个应用内部仍按自己的单实例规则运行。
- 不在操作系统全局注册的 `lexora-attachment:` 等内部协议可以保留。系统级 URL 协议、文件关联如实际存在，另行核对，不能抢占 Lexora 注册项。

## 5. 安装与 Windows 沙盒服务

### 5.1 安装身份

独立核查应用标识、安装目录、可执行文件、快捷方式、卸载注册项、通知身份和自启动项。源码里的内部包名可保留，但安装器不能因此仍判断 XTLaw 就是 Lexora。

XTLaw 不覆盖 Lexora；XTLaw 后续自己的版本升级应保留自己的数据，不产生重复卸载项。

### 5.2 服务隔离

本次服务名为 `XTLawSandboxNetwork`，管道为 `XTLawSandboxNetwork-v1`，容器前缀为 `XTLaw.Sandbox.`，卸载注册键为 `XTLawSandbox`。防火墙提供者与子层的固定 GUID（系统资源标识）也独立于 Lexora，防止安装恢复或卸载误清上游规则；不能只改服务显示名。

- 安装或启动 XTLaw 不替换、停止或重配置 Lexora 的沙盒服务。
- 卸载 XTLaw 只能清理自己的服务、安装文件和注册项；反方向同样验证。
- 保持现有沙盒权限和访问控制强度，不通过放宽权限、绕过沙盒解决冲突。
- 服务安装需操作系统授权；失败时保留原有安全失败方式并提示原因，不自动退回无沙盒执行。
- 测试不得操作真实正式版服务。
- 正式版与开发版采用受控共用 XTLaw 沙盒组件：保留现有协议与完整二进制 SHA-256（内容指纹）一致性检查。内容不一致时报告需要修复，不能直接复用不匹配的服务；安装/修复仍由用户显式操作、经过系统授权，并保留活动任务阻止替换的检查。不同沙盒二进制的正式版与开发版不承诺同时可用；本次不扩展开发版独立服务。测试只运行纯函数断言，不操作真实服务。
- 保留现有按用户命名的全局 ACL 锁（文件权限修改协调锁）与 Lexora 协调。它不共享配置、会话或服务，只防止两者访问同一份用户主动选择的文件时并发改写权限。不能为追求名字不同而拆开这一安全协调锁。

**仅隔离数据而不处理全局服务，不满足本规格的双应用目标。**

## 6. 更新、品牌与许可

- 更新检查、下载和反馈使用 `https://github.com/QAyong/XTLaw` 对应入口，不把 Lexora 的 Release 当作 XTLaw 更新。
- 首个正式发布前明确版本标签与版本比较策略；没有有效 XTLaw Release 时应正常显示无可用更新或清晰提示，不跳回上游。
- 保留 Spec-022 的品牌图片、关于页、来源说明与许可证要求。用户界面以 XTLaw 为主，来源说明可集中在“关于/开源许可”入口，无需每个设置页重复展示。
- 当前许可为 `AGPL-3.0-only`。商业收费不自动解除许可证、署名和对应源码提供义务；发布二进制时提供匹配版本的源码入口，并核查随附第三方许可。
- 不因二次开发就默认获得闭源权利；闭源路线或特殊商业授权需另行确认权利基础。本方案不替代专业法律意见。

## 7. 以后手动迁移旧数据

本阶段 XTLaw 首次启动是全新应用，不自动读取 `.lexora`。旧数据仍在，只是新应用看不到。

迁移时另开任务，按以下步骤处理：

1. 关闭两个应用及写入相关数据的进程，确定源、目标和数据版本。
2. 分别备份 Lexora 源数据与 XTLaw 目标数据，检查备份可读取。
3. 按实际结构选择配置、会话、空间引用、技能和插件；检查绝对路径及授权记录，不直接整目录覆盖。
4. 不搬缓存、锁、socket、命名管道、临时文件和系统服务。
5. 加密凭据是否能迁移单独验证；不能解密时重新填写模型密钥或重新登录，不降低加密保护。
6. 启动 XTLaw，检查会话、模型和文件访问；原 Lexora 数据保持不动。
7. 如果失败，恢复 XTLaw 的迁移前备份，不改变 Lexora 源数据。

以后只有出现其他用户和真实迁移需求，才考虑产品化导入功能。

## 8. 实施顺序与变更控制

### 阶段一：建立基线并隔离数据与运行身份

1. 确认当前 Git 状态，记录已有改动，不擅自清理用户工作区。
2. 先跑相关路径、启动和原生组件测试，记录命令、范围与结果，建立同口径基线。
3. 实现主目录、命名空间、Electron 存储、凭据及环境变量规则。
4. 同步子进程、原生组件、通信路径和测试保护。
5. 运行定向测试与桌面构建。

### 阶段二：隔离安装与系统资源

1. 完成 Windows 沙盒服务及安装卸载的联动修改。
2. 检查自启动、通知、单实例、系统注册项及安装标识。
3. 助手完成类型检查、桌面构建和定向检查；安装包另行按需生成，双应用真实安装验证由用户执行。
4. 更新本规格及 Spec-022 的实际完成状态；未通过的项目保持未勾选。

每阶段保持清晰的修改范围，避免把品牌补漏与隔离混成不可辨认的大补丁。提交、推送、创建备份标签或重置工作区均不默认执行；提交需用户明确要求或同意。失败时保留证据，只撤销本次改动，不使用全量回退清理其他工作。

预期不需要新增依赖。若实际修改依赖，按仓库约定先执行 `pnpm install`（安装依赖）。

建议验证命令：

```powershell
# 桌面类型检查
pnpm --filter @uselexora/lexora-buddy type-check

# 构建桌面应用
pnpm --filter @uselexora/lexora-buddy build

# 正式发布时按需执行完整预检；本轮不运行全量测试与打包链路
pnpm check:buddy

# 需要安装包时另行执行；不代表已安装或验收
pnpm --filter @uselexora/lexora-buddy package:windows
```

定向测试按实际文件补充。测试有失败时必须与同命令、同范围的基线比较，不把不同测试范围的失败数量直接对照。无法解释的新增失败不能标注为“已通过”。

## 9. 验收标准

### 数据与运行

- [ ] 在含有 Lexora 旧数据的电脑上首次启动 XTLaw，不显示旧会话、不自动导入、不修改旧数据。
- [ ] XTLaw 配置和会话只写入 `.xtlaw`，Electron、缓存和状态目录也独立。
- [ ] 在任意一个应用修改模型、设置和会话，不影响另一个。
- [ ] 正式版、开发版和测试版落点符合第 4 节；测试不能覆盖真实数据。
- [ ] 桌宠、浏览器适配器和原生宿主均使用 XTLaw 路径与通信端点。
- [ ] 两个应用同时运行，各自的启动、通知、文件访问和沙盒命令正常，不抢单实例锁或通信端点。
- [ ] 继承旧 `LEXORA_*` 环境变量不会让 XTLaw 隐式写入 Lexora 数据；显式覆盖保护按设计生效。

### 安装、更新与卸载

- [ ] 两个应用可同时安装，安装目录、快捷方式、自启动和卸载项区分明确。
- [ ] 各自的沙盒服务可正常工作，安全约束未被削弱。

- [ ] 在有备份或可恢复测试环境中，分别验证卸载 XTLaw 与卸载 Lexora，剩余应用及其沙盒仍可用。

- [ ] 更新来源只属于 XTLaw，无 Release 和网络失败场景得到合理处理。

### 工程与发布

- [x] 已运行的定向测试无新增失败，类型检查和 Windows 桌面构建通过，结果有记录；不代表全量测试或发布预检通过。
- [ ] Windows 安装包生成完成，真实安装、运行和卸载实测完成。
- [ ] 来源、许可证及匹配版本源码入口满足发布要求。
- [ ] 验收记录注明平台、版本、命令、结果和未解决项；“编译通过”不替代“并行安装与卸载实测”。

Windows 是本阶段优先实测平台。Linux/macOS 路径规则需测试；未经对应平台安装验收，不宣称已完成该平台双应用兼容。

## 10. 未决事项与风险

核心方向已确定：两个独立应用；不写自动导入；以后手动搬旧数据；不全面重命名源码。

实施前还需确定的细节：

1. 首个 XTLaw 正式 Release 的版本号，以及无 Release 时的更新提示策略，本轮不改版本或发布。
2. 本阶段是否仅发布 Windows；其他平台没有构建与实测就保留待验收状态。

已落实的实现选择：对外使用第 4.2 节 XTLaw 环境变量；开发版与正式版按第 5.2 节的相同二进制、显式修复策略受控共用 XTLaw 沙盒服务。

主要风险是路径遗漏、全局资源冲突和凭据不可直接复制。通过父子进程一致配置、同口径测试基线、双应用安装卸载实测和后续备份迁移控制风险；不通过自动迁移或大范围改名扩大本次范围。
