# Bug：主、子代理竞争网页工具并发额度，触发 `WEB_BUSY` 后未排队导致检索遗漏

**日期**：2026-10-27  
**优先级**：中（P2）  
**状态**：已由上游 `901d7704e` 修复并移植（2026-10-28），本地的 `WebConcurrencyGate` 已撤销；下文的本地方案仅作历史记录  
**上游基线**：`18f424031`（2026-10-27）。上游同一处代码与本地一致，同样存在此问题。  
**范围**：网页搜索与抓取的并发调度；不改 4 / 2 这两个并发上限。

## 现象

AI 中转站法律检索时，主代理同时发起 4 个搜索，子代理随后抓取一篇微信公众号文章，约 5 毫秒返回 `WEB_BUSY`；重试时又被 4 个抓取占满，约 26 毫秒再次返回 `WEB_BUSY`。两次返回均为：

```json
{ "ok": false, "provider": null, "code": "WEB_BUSY", "attempts": [], "availableProviders": [] }
```

用户追问后单独抓取同一篇文章，约 946 毫秒成功；用第一次失败的旧链接原样重试，约 887 毫秒成功。失败并非微信拒绝访问，而是请求在进入抓取后端前被本地并发限制拒绝，最终被当作“正文获取失败”交付。

## 原因

- 搜索和抓取共用 `WebCapabilityService.#run` 的同一个计数器，`#active >= 4` 时立即返回 `WEB_BUSY`，不排队，且发生在任何后端执行之前。
- 宿主侧另有两处同样的立即拒绝：同时进行的请求超过 8 个、页面渲染超过 2 个（`registerWebHostRpc.ts`）。抓取需要渲染的页面时，会先撞上更小的 2。
- codemode 允许同时 16 个工具调用、排队 128 个（`codemodeExtension.ts`），上游放得宽、网页服务收得窄，放大了冲突。主、子代理各有独立会话和 codemode，只有网页服务这一层能看到全部请求。
- 日志和耗时数据来自当次会话，本次未复核；代码层面已确认拒绝机制。

## 修复

- 新增 `WebConcurrencyGate`：满额后进入有界等待队列，最长等待 30 秒，队列最多 64 个，再多才返回 `WEB_BUSY`。
- `#run` 先取名额再执行；90 秒执行超时在拿到名额后才开始计时，排队时间不占用。
- 页面渲染（最多 2 个）在服务层同样排队，不再把第 3 个渲染送到宿主被拒。
- 排队中被取消或关停时立即退出队伍并释放，不占名额。
- 新增错误码 `WEB_QUEUE_TIMEOUT`（排队超时，尚未访问目标网站），与目标网站失败区分；新增诊断阶段 `queued`，`started` 带上排队耗时。
- 4 和 2 的上限保持不变；等排队耗时有数据后再决定是否调整。

## 验收

- 一次提交 6 个请求，同时执行不超过 4 个，其余依次完成（`WebCapabilityService.spec.ts`）。
- 排队中取消后返回 `WEB_CANCELLED`，名额不泄漏，后续请求正常执行。
- 排队超过 30 秒返回 `WEB_QUEUE_TIMEOUT`，`attempts` 为空。

## 未验证

- 未做渲染排队的专门测试；宿主 8 个请求的上限仍是立即拒绝，但服务层 4 个操作各自的并行请求通常不会超过它。
- 未跑全量测试，仅跑 `service/src/web`、`shared` 的 vitest、`eslint` 和 `tsc -p tsconfig.node.json`。
