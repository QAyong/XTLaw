# Bug：长对话生成中切换回来后，向上滚动会突然跳到很上面

**日期**：2026-11-07
**优先级**：中（P2。不丢消息，但长对话里正在生成时，切走再回来就很难向上阅读）
**状态**：待修复。本次只记录，没有改代码。已向上游报告：[useLexora/Lexora#589](https://github.com/useLexora/Lexora/issues/589)。
**范围**：桌面端聊天正文的虚拟列表滚动。短对话、没有切走过的当前对话、以及已经停在历史位置再切走的场景，不在本次现象里。

## 现象

长对话里 AI 还在运行时：

1. 点到另一个对话。
2. 再点回来。
3. 向上滑动，想看刚生成的上面几条消息。

视口会突然跳到比手指或滚轮移动量更靠上的位置，不是平滑地跟着滚。

## 预期

向上滚多少，就只移动多少。正在生成的内容可以继续往下长，但不能把已经离开底部的阅读位置再往上甩。

## 原因

切对话会拆掉当前的虚拟列表，已测量的行高一起丢掉。回来后列表按估算高度重新排，并且因为 AI 还在跑，视口重新钉在底部。此时底部附近几行会测到真实高度，再往上的行仍是估算值。用户再向上滚，这些没测过的行第一次测高，滚动补偿把视口多往上推了一截。

相关代码：

- `apps/buddy/src/modules/tasks/widgets/transcript/BuddyChatMessageList.vue` 用 `` `${conversationId}:${activeBranchId}` `` 作为 `BuddyChatTranscriptViewport`（聊天正文视口）的 `key`。对话一切换，视口组件重新挂载，`@tanstack/vue-virtual` 里的 `itemSizeCache`（已测量行高缓存）清空。
- `apps/buddy/src/modules/tasks/widgets/transcript/useChatTranscriptViewport.ts` 的 `estimateHeight()` 给用户消息估 160、助手消息估 320、活动行估 64。长对话里很多短行比这个矮。
- 同一文件把虚拟列表设成 `anchorTo: 'end'`（从底部锚定），并且在跟随底部时打开 `followOnAppend`（末尾追加时继续跟随）。AI 还在跑时，`following()` 为真，回来后会重新滚到末尾。
- 依赖的 `@tanstack/virtual-core@3.19.10` 在 `resizeItem()` 里：行第一次测高时，只要行顶在视口上方（`itemStart < scrollOffset`）就按整段高度差补偿滚动。横跨视口上沿的行也算在内。向上滚动过程中的再次测高则不再补偿。

因此回来之后：

1. 只有当时在视口和少量预渲染范围内的行被测成真实高度，再往上仍是偏大的估算。
2. 用户向上滚进这批未测量的行。
3. 横跨视口上沿的行被当成“整行都在上方”做了全额补偿，视口比内容实际上移得更多，看起来就是突然跳到更上面。
4. 若行第一次测到的高度是 0（内容还没排完，但元素已经挂上），这个 0 会被记进缓存。向上滚时随后到来的真实高度不再补偿，跳上去的位置留不住。`useChatTranscriptViewport.ts` 的 `measureElement` 在高度为 0 但 `offsetParent` 存在时会直接返回 0，绝对定位的行很容易走这条路径。

## 证据与边界

用 `@tanstack/virtual-core@3.19.10` 的 `Virtualizer` 加一个假滚动容器做了机制复现，不是桌面应用里的实测：

- 200 行，估算高度 320，真实高度 80，视口高 800。先滚到末尾，并像界面那样把末尾可见范围测完。
- 再向上滚 400 像素，然后测量新进入范围的行。
- 库的默认补偿：作为阅读锚点的那一行在屏幕上下移了 240 像素，也就是视口多往上跳了一行的估算误差。滚动位置从 59680 掉到 58480，比用户滚动量多掉了 1200 里的补偿和这次错位。
- 若第一次测高先记成 0、向上滚动期间再记成真实高度，滚动位置再往上掉一截，而且不会补回来。
- 只补偿“整行都在视口上方”的第一次测高时，同一锚点的屏幕位置不变。

没有在 XTLaw 桌面窗口里按用户步骤复现，也没有改代码验证修复。上面的数字只说明补偿规则会把视口多往上推，不能当成用户机器上的实际跳动量。

现有阅读测试 `.playwright/scripts/__tests__/reading.e2e.mjs` 覆盖了“生成中直接向上滚”和“先滚到历史位置再切对话”，没有覆盖“生成中、停在底部、切走再回来、然后再向上滚”。

## 建议修复方向

下次会话再改，本次不动代码。方向按优先级：

1. 第一次测高只补偿整行都在视口上方的行，不要补偿横跨视口上沿的行。跟随底部时，库自己的 `wasAtEnd`（仍在末尾阈值内就按总高度差钉住底部）可以保持不动。
2. 行还没排完时测到的 0 不要写入行高缓存，先沿用估算高度，等真实高度到来再记。
3. 切对话时保留已测量行高，回来后不要从 160/320 重新估算。宽度变化后仍要以重新测量为准，缓存只作估算，不能当成永久高度。

不要为了压住这次跳动而去掉底部跟随，也不要在用户已经向上阅读时强制 `scrollToEnd()`。

## 验收

- 长对话，AI 仍在生成，切到另一个对话再回来，停在最新内容。向上小步滚动：视口只移动滚轮的量，不突然跳到更早的消息。“回到最新”可以出现。
- 停在历史位置后，生成内容继续变长，阅读位置不被拽走。这是现有阅读测试已经要求的行为。
- 点“回到最新”仍能回到底部，并在仍停留在底部时继续跟随。
- 关闭分屏后，正文和滚动位置仍在。这是 `useChatTranscriptViewport.ts` 里按 `scrollOffset` 回写 `scrollTop` 要保住的行为，修复时不要拆掉。
- 短对话、内容矮于一屏时，切回来仍贴在底部，不出现空白或跳到顶部。

## 文件与术语说明

| 原名称 | 中文含义 | 用途 |
| --- | --- | --- |
| `BuddyChatMessageList.vue` | 聊天消息列表 | 按对话和分支给正文视口加 `key`，切换时会重新挂载 |
| `useChatTranscriptViewport.ts` | 聊天正文视口逻辑 | 估算行高、测量行、跟随底部 |

| `wasAtEnd` | 仍在末尾阈值内 | 跟随底部时按总高度差保持贴底 |
