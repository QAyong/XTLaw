# Spec-022：XTLaw 品牌替换与发布迁移方案

**日期：** 2026-10-06

**状态：** 已按默认方案完成本地代码改造；桌面端与官网构建通过，按用户要求未生成安装包、未提交、未推送。

**当前仓库：** `origin` 已由 `QAyong/Lexora` 更名为 `QAyong/XTLaw`；`upstream` 继续保留 `useLexora/Lexora`，用于同步原项目。

## 1. 背景与目标

当前项目是在 Lexora 基础上的二次开发版本，计划采用 **XTLaw** 作为对外品牌。仓库虽然已经更名，但桌面应用、安装包、官网、更新检查、反馈入口、图标和说明文档仍主要使用 Lexora 上游信息。

> 实施记录（2026-10-06）：已完成本文所列第一阶段代码、配置、文案和品牌资源替换；保留 `.lexora` 数据目录、内部协议、环境变量及底层兼容名称。已执行桌面端和官网构建。Windows 打包在进入下载阶段时按用户要求中止，因此没有生成新的安装包。

本方案的目标是先完成用户能够看到和接触到的品牌迁移，同时保持现有功能、数据和上游同步能力稳定：

- 桌面软件、安装包、官网和文档统一显示 XTLaw。
- 下载、更新检查、问题反馈和源码地址统一指向 `QAyong/XTLaw`。
- 使用用户提供的 XTLaw SVG 建立完整的桌面与网站图标资源。
- 保留原项目许可证、来源说明和必要署名。
- 第一阶段不全面重命名内部类型、协议、环境变量和数据目录，避免无用户价值的大范围改造。

## 3. 范围边界

### 3.1 第一阶段包含

- 桌面应用可见名称、窗口标题、关于页、聊天身份和中英文界面文案。
- Windows 安装包名称、可执行文件、快捷方式、卸载项和应用标识。
- 应用图标、任务栏图标、系统托盘图标、开发/测试变体、启动页品牌图和网站 favicon。
- 应用包元数据中的官网、仓库、作者/维护者和问题反馈地址。
- 更新检查、Release 页面、反馈 Issue 和帮助文档入口。
- 官网、README、下载链接和 GitHub Pages 配置中的仓库地址与品牌名称。
- “基于 Lexora 修改”的来源说明、修改声明、许可证入口和源码入口。
- Windows 桌面构建与安装包验证。

### 3.2 第一阶段不包含

- 不全局替换所有 `Lexora` 字符串。
- 不重命名 `LexoraDesktopApi` 等 TypeScript 类型和公共接口。
- 不修改 `lexora-attachment:`、`lexora-artifact:`、`lexora-extension:` 等内部协议。
- 不修改 `LEXORA_HOME`、`LEXORA_BUDDY_PROFILE` 等环境变量。
- 不重命名 Rust 包、原生二进制、数据库结构和历史迁移。
- 不迁移或删除现有 `.lexora` 用户数据。
- 不重新设计产品功能、桌宠系统或网站信息架构。

这些内部名称不会直接展示给普通用户。后续只有在确有发布、兼容或维护收益时，才单独立项处理。

## 4. 品牌资源方案

用户已提供四份 2048×2048 SVG：

| 源文件 | 建议用途 |
| --- | --- |
| `XTlaw_white_on_black.svg` | 深色背景上的完整品牌字标 |
| `XTlaw_black_on_white.svg` | 浅色背景上的完整品牌字标 |
| `XT_white_on_black.svg` | 深色背景上的简化标志 |
| `XT_black_on_white.svg` | 浅色背景上的简化标志 |

现有 SVG 都包含实色方形背景，且标志横向较宽。它们可以作为品牌母版，但不宜未经调整直接缩成 16～32 像素的任务栏或托盘图标，否则主体会显得过小。

### 4.1 需要生成的最终资源

| 目标资源 | 尺寸 | 用途 | 处理要求 |
| --- | --- | --- | --- |
| `app-icon.png` | 512×512 | 正式版应用及安装包 | 使用放大后的 XT 标志，保留安全边距和透明区域 |
| `app-icon-dev.png` | 512×512 | 开发版 | 正式版基础上增加清晰的 `DEV` 标识 |
| `app-icon-test.png` | 512×512 | 测试版 | 正式版基础上增加清晰的 `Test` 标识 |
| `tray-icon.png` | 256×256 | 正式版系统托盘 | 针对小尺寸重新构图，不直接等比缩小完整字标 |
| `tray-icon-dev.png` | 256×256 | 开发版托盘 | 增加 `D` 或等价开发标识 |
| `tray-icon-test.png` | 256×256 | 测试版托盘 | 增加 `T` 或等价测试标识 |
| 品牌头像/启动图 | 1254×1254 | 启动页及聊天身份 | 建议使用方形品牌构图，不强行拉伸完整字标 |

第一阶段沿用仓库当前资源尺寸和引用关系，不新增图标生成框架。最终资源应分别写入品牌真源和运行时副本，并保持构建校验要求的一致性。

## 5. 代码与配置修改范围

### 5.1 仓库、官网和产品链接

- `apps/buddy/package.json`
  - `productName` 改为 `XTLaw`。
  - `desktopName` 改为确认后的应用标识。
  - `homepage` 改为 XTLaw 官网。
  - `repository` 改为 `QAyong/XTLaw`。
  - `bugs` 改为 `QAyong/XTLaw/issues`。
  - 维护者信息改为用户确认的信息，同时不删除原项目来源说明。
- `apps/buddy/electron/shared/productLinks.ts`
  - 更新检查和反馈继续从 `package.json` 的仓库地址派生。
  - 文档地址不再错误拼接上游官网。
- `apps/website/src/.vitepress/productLinks.ts`

- `README.md`、`README.en.md` 和快速开始文档
  - 官网、下载、Release、Issue、CI 徽章和指南链接统一指向 XTLaw。

仓库已经存在 GitHub Pages 工作流，会根据仓库 Pages 的实际基础路径构建网站。首次发布前需要在 GitHub 仓库设置中确认 Pages 允许由 GitHub Actions 部署。

### 5.2 桌面应用与安装包

- `apps/buddy/electron-builder.config.cjs`
  - 更新 App ID、显示名、Windows 可执行文件、快捷方式、卸载项、Linux 包名和说明。
- `packaging/buddy/release/artifacts.mjs`
  - 安装包文件名改为 XTLaw。
- `packaging/buddy/windows/installer.nsh`
  - 安装日志名和用户提示中的产品名改为 XTLaw。
- `apps/buddy/electron/main/paths.ts`
  - 稳定版、开发版和测试版的 `appName` 改为 XTLaw。
  - 第一阶段保留 `namespace` 和 `.lexora` 数据目录，避免已有数据消失。

### 5.3 用户可见文案

优先修改真正显示给用户的内容：

- `apps/buddy/index.html` 的窗口标题。
- 中英文 `i18n` 中的产品名、助手名、错误提示和设置说明。
- 关于页、更新弹窗、启动页和聊天消息身份。
- 官网标题、导航、首页正文和指南中的品牌名称。

源码类型、类名、测试工具变量及内部错误码不因“看起来还有 Lexora”而机械替换。每一处修改都应先判断是否对外显示或参与持久化/跨进程协议。

### 5.4 更新检查与发布

桌面更新检查会读取 `package.json` 中的仓库地址并查询 GitHub Releases。迁移后应满足：

- 更新来源只能是 `QAyong/XTLaw`。
- Release 页面必须属于 `QAyong/XTLaw`。
- 正式版本继续使用 `v版本号` 标签格式，例如 `v0.9.5`。
- XTLaw 第一个正式 Release 发布前，默认关闭自动更新提示，或确保仓库已有可解析的正式 Release。
- 旧仓库 URL 的 GitHub 重定向只作为过渡，应用和文档不能长期依赖旧地址。

## 6. 数据兼容策略

第一阶段建议使用“外部品牌已迁移，内部数据路径保持兼容”的方式：

```text
软件显示：XTLaw
安装标识：新的 XTLaw App ID
数据目录：继续读取 ~/.lexora
内部协议：继续使用 lexora-* 名称
```

优点：

- 已有模型配置、会话、空间、授权和设置可继续使用。
- 不需要在品牌替换中同时实现数据迁移与回滚。
- 上游更新更容易合并，变更文件较少。

代价：

- 高级用户仍可能在目录、环境变量或日志中看到 Lexora 内部名称。
- 如果未来改为 `.xtlaw`，仍需要一次独立迁移。

若用户希望两个软件能够并行安装并完全隔离，则应在实施前改为新数据目录、新命名空间和新的迁移策略，不能在发布后临时切换。

## 7. 许可证、署名和品牌边界

项目当前使用 `AGPL-3.0-only`。第一阶段应：

- 保留根目录 `LICENSE`，不得把原许可证删除或替换为闭源许可证。
- 在 README 和应用“关于”页面明确说明 XTLaw 基于 Lexora 修改。
- 标明主要修改者和开始修改日期，不把原项目表述为完全由 XTLaw 从零开发。
- 发布安装包时提供对应版本的源码入口。
- 如果修改后的服务允许其他用户通过网络使用，提供明显的对应源码获取入口。
- 保留第三方组件随附的许可证文件。

本节是工程合规方案，不替代针对商业发布、商标或特定司法辖区的专业法律意见。

## 8. 实施顺序

1. **确认关键命名**：确认软件显示名、应用标识、维护者名称、官网地址和数据兼容方案。
2. **准备品牌资源**：从四份 SVG 生成应用、托盘、启动页、开发/测试和 favicon 资源，先做视觉预览。
3. **迁移仓库与链接**：更新包元数据、官网、下载、更新、Issue、CI 徽章和文档地址。
4. **替换桌面可见品牌**：窗口、关于页、聊天身份、中英文界面和通知文案。
5. **更新打包身份**：Windows App ID、EXE、快捷方式、卸载项和安装包名称。
6. **补充来源与许可说明**：README、关于页和源码入口。
7. **最小验证**：先构建桌面应用；通过后再执行 Windows 打包，不为了品牌替换扩大测试范围。
8. **用户查看**：检查任务栏、托盘、启动页、聊天头像、关于页、安装程序和官网。

不修改依赖，因此方案预期不需要新增包或执行依赖安装。实施完成后优先执行：

```powershell
pnpm --filter @uselexora/lexora-buddy build
pnpm --filter @uselexora/lexora-buddy package:windows
```

如果品牌变更涉及工作区包名，再按仓库规则同步脚本和锁文件；不能只改包名而遗漏过滤器。

## 9. 验收标准

### 桌面应用

- [ ] Windows 窗口、任务栏、快捷方式和卸载列表显示 XTLaw。
- [ ] 正式版、开发版和测试版图标可以明确区分。

- [ ] 启动页、聊天头像、关于页和更新弹窗不再展示旧品牌图片。
- [ ] 中文和英文主要界面不再向普通用户显示 Lexora Buddy。

### 链接与发布

- [ ] 官网打开 XTLaw 页面，不再进入 `uselexora.app`。
- [ ] 下载、更新检查和 Release 页面只指向 `QAyong/XTLaw`。
- [ ] 反馈按钮打开 `QAyong/XTLaw/issues/new`。
- [ ] 帮助按钮打开有效的 XTLaw 使用指南。
- [ ] README 徽章和链接不再统计或跳转到上游仓库。

### 兼容与合规

- [ ] 原 `.lexora` 中的现有配置和会话仍可读取。
- [ ] `upstream` 远端仍可正常获取原项目更新。
- [ ] README 和关于页包含基于 Lexora 修改及 AGPL 许可说明。
- [ ] Windows 应用构建和安装包生成通过。

## 10. 实施前需要用户确认

1. 软件最终显示名使用 `XTLaw`，还是 `XTLaw Desktop` / `XTLaw Buddy`？本方案默认 `XTLaw`。
2. 维护者显示为 `XTLaw`、`QAyong`，还是中文姓名？
3. 是否接受暂时使用 `https://qayong.github.io/XTLaw/` 作为官网，并启用 GitHub Pages？
4. 是否继续读取 `.lexora` 数据？本方案默认继续读取，以免原有配置和会话消失。
5. 聊天助手头像使用 XT 品牌标志，还是另行提供人物/头像资源？

用户确认以上内容后，按第 8 节顺序实施。若只确认其中一部分，则先做已确认且可独立回退的部分，不擅自扩大到内部全面重命名。
