## 1. 摘要

PI-Desktop 新增内置插件 `pi.office`。用户从聊天文件引用或文件列表点击 `.docx` 时，右侧工作面板直接打开可视化编辑器。用户可以修改文档，并通过 `Ctrl+S` 保存回原文件。

编辑器能力来自 GenOffice 的 DOCX 编辑层，但不引入 GenOffice 的整套 Electron 桌面应用、AI、MCP、账户系统或在线服务。PI-Desktop 宿主只负责以下事情：

1. 判断某个 DOCX 应交由哪个插件打开。
2. 打开对应插件视图并传递文件位置。
3. 管理标签页、关闭确认和应用生命周期。
4. 提供受控的插件文件读写边界。

DOCX 的解析、页面渲染、编辑、序列化和保存由 `pi.office` 插件负责。

第一阶段不接 XLSX、PPTX 和 PDF。四种格式共用一个插件外壳的长期方向不变，但一次只交付一种格式，避免编辑器引擎、保存兼容、字体资源和平台打包风险同时进入主线。

---

## 2. 背景与问题

PI-Desktop 当前已有文件查看能力，但 Office 文件需要完整的可视化编辑体验。普通文本查看器无法满足 DOCX 的段落、表格、图片、样式和分页等结构。

用户期望的工作方式不是：

1. 点击文件。
2. 跳转到外部程序或独立窗口。
3. 编辑后回到 PI-Desktop 查看结果。

用户期望的是：

1. 点击文件。
2. 文件直接在 PI-Desktop 右侧工作面板打开。
3. 直接编辑。
4. 保存回原路径。
5. 后续修改沿用上一版，不需要用户反复导出和导入。

因此，本方案将 DOCX 编辑能力作为 PI-Desktop 的插件视图交付，而不是作为外部 companion 应用、MCP 服务或命令行工具交付。

## 3. 产品目标

### 3.1 第一阶段目标

- 从聊天文件引用点击 `.docx`，在右侧面板打开预览和编辑器。
- 从 `pi.file-manager` 点击 `.docx`，走同一套打开逻辑。
- 支持基础文档编辑。
- 支持保存回原文件。
- 支持未保存修改提示。
- 支持外部修改冲突检测。
- 插件未启用、不可用或文件不支持时，回退到原有文件查看器。
- 在 Windows、macOS、Linux 上保持同一套编辑页面和协议。

### 3.2 第一阶段编辑范围

建议将第一阶段的“可保存”范围限定为：

- 正文文字。
- 段落和换行。
- 粗体、斜体、下划线等基础字符样式。
- 标题层级。
- 有序和无序列表。
- 基础表格。
- 超链接。
- 图片。
- 撤销和重做。
- 基础页面预览。

### 3.3 第一阶段明确不做

| 不做的能力 | 原因 |
| --- | --- |
| XLSX 编辑 | 需要 Univer、网关和 Rust sidecar，另立阶段 |
| PPTX 编辑 | 需要 Konva、元素模型和独立回写验证，另立阶段 |
| PDF 编辑 | PDF 的“编辑”语义不同，需要单独定义批注、表单和页面操作 |
| 宏执行 | 安全风险高，不应在插件沙箱内执行 |
| 云文档和多人协作 | 第一版坚持全本地，不引入网络依赖 |
| GenOffice AI、MCP、账户 | 与 DOCX 编辑无关，扩大权限和攻击面 |
| 完整 Word 兼容 | 复杂域、修订、嵌入对象等需要单独做保真矩阵 |
| 移动端和 Web 端 | 当前宿主依赖 Electron 视图和本地文件能力 |

## 4. 关键假设与约束

1. PI-Desktop 继续使用 Electron 桌面进程模型，插件页面运行在宿主的沙箱化视图内。
2. `pi.office` 第一版作为随应用发布的内置插件，用户可以禁用。
3. 编辑页面不能直接访问 Node.js 或文件系统，所有文件操作经过插件主进程。
4. 宿主是文件打开路由的唯一决定者，插件不能自行扫描或猜测用户想打开哪个文件。
5. DOCX 文件在编辑过程中可能出现外部程序修改，保存前必须做冲突检查。
6. GenOffice 的编辑器包不是可直接安装的公开 npm 依赖，第一版需要固定上游提交并维护 vendored 代码和许可证。
7. 第一阶段只做本地文件，不发起网络请求，不加载远程字体和远程脚本。

## 5. 总体架构

```text
用户操作
  |
  v
PI-Desktop Renderer
  |
  | 请求打开文件 / 维护工作面板标签
  v
Electron Main / Host
  |
  | 解析文件关联并创建插件视图
  v
插件视图 pi.office/editor
  |
  | pluginBridge 调用
  v
pi.office 插件主进程
  |
  | 读取、序列化、保存、冲突检查
  v
DOCX 文件
```

### 5.1 分层责任

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| Renderer | 点击入口、标签页、关闭确认、面板 UI | 解析 DOCX、直接读写文件 |
| Electron Main | 文件关联解析、视图生命周期、桥接授权 | DOCX 格式逻辑 |
| 插件视图 | 编辑器 UI、交互、脏状态 | 直接访问文件系统 |
| 插件主进程 | 文件读取、序列化、保存、冲突检查、原子写入 | 宿主标签页管理 |
| GenOffice 适配层 | 把编辑器文件接口转换为 `office.*` 桥接调用 | PI-Desktop 权限和生命周期 |

### 5.2 为什么不直接复用 GenOffice 桌面应用

GenOffice 的 Electron 壳包含它自己的窗口、IPC、设置、AI、MCP 和服务管理。直接复用会让两个桌面应用争夺文件、进程和窗口生命周期，也会把不相关的网络和账户能力带入 PI-Desktop。

正确做法是只复用编辑器和格式引擎，并在适配层替换宿主文件接口。

## 6. 文件关联机制

### 6.1 建议新增的插件声明

为了让宿主不再硬编码 `pi.office`，插件清单增加 `fileAssociations`。

```ts
contributes: {
  fileAssociations: [
    {
      extensions: ["docx"],
      view: "editor",
      priority: 100
    }
  ]
}
```

具体字段名和校验规则应在实现前由 ADR 固定。本文建议的语义如下：

- `extensions`：小写、无点号的扩展名列表。
- `view`：必须引用同一插件已声明的 `contributes.views` 视图。
- `priority`：同扩展名有多个处理者时，数值更高的优先。
- 关联只表示“优先打开方式”，不授予文件权限。
- 文件关联停用时，宿主必须回退到原有查看器。

### 6.2 打开解析顺序

1. 用户点击文件。
2. 宿主解析文件真实路径、扩展名和当前会话上下文。
3. 宿主查找已启用、已授权且声明该扩展名的插件。
4. 按优先级选择视图。
5. 若没有可用关联，使用 `pi.file-manager` 或宿主原文件查看逻辑。
6. 若关联插件打开失败，向用户提示错误，并允许回退打开。

### 6.3 为什么第一版也需要通用关联协议

只在宿主中硬编码 `pi.office` 可以更快做出演示，但会把文件类型、插件 ID 和面板逻辑绑死。以后接 XLSX、PPTX、PDF 或第三方文档插件时，又要重新改宿主。

第一期就建立通用文件关联，改动更大，但边界更稳定，也更容易回退和测试。

## 8. 插件开放接口

插件页面与插件主进程之间只开放最小文档接口。接口名称是建议，最终应写入插件 API 规范。

```text
office.read
office.save
office.checkConflict
office.reload
office.confirmClose
office.getSettings
office.setDirty
```

### 8.1 `office.read`

输入：

- 宿主授权打开的文件路径。
- 可选的显示名称和 MIME 类型。

输出：

- 文档句柄。
- 原文件元数据。
- 编辑器加载需要的数据。
- 当前文档是否只读。

大文件不应通过单次超大 IPC 消息传输。接口从第一版就应支持分块读取或临时传输句柄，避免编辑器打开时造成主进程和渲染器卡顿。

### 8.2 `office.save`

输入：

- 文档句柄。
- 编辑器序列化后的 DOCX 数据。
- 打开时记录的原文件版本指纹。

输出：

- 成功或失败。
- 新文件元数据。
- 新的版本指纹。

保存必须由插件主进程执行，不能由编辑页面直接写入路径。

### 8.3 `office.checkConflict`

比较对象至少包括：

- 文件大小。
- 修改时间。
- SHA-256 内容哈希。

任一项变化都视为外部修改。用户可以：

- 重新加载磁盘版本。
- 明确选择覆盖。
- 取消保存。

第一版默认选择应是“重新加载或取消”，不能默认覆盖。

### 8.4 `office.confirmClose`

关闭文档标签或退出应用前，若文档处于 dirty 状态，宿主必须调用该接口或读取宿主已缓存的 dirty 状态，要求用户选择：

- 保存后关闭。
- 放弃修改。
- 取消关闭。

不能通过关闭视图来隐式丢弃修改。

## 9. GenOffice 集成方式

### 9.1 固定上游

- 上游仓库：GenOffice。
- 固定提交：`d1280d153362071de433a6439ca31585af4af8f7`。
- 不跟随上游 `main` 自动升级。

### 9.2 复用范围

DOCX 相关编辑器、文档模型、序列化和基础渲染层可以复用。以下内容不进入第一版：

- GenOffice Electron 主进程。
- GenOffice 窗口和菜单系统。
- GenOffice 的账户和设置系统。
- GenOffice AI 和 MCP 功能。
- GenOffice 的远程服务。

### 9.3 适配层原则

GenOffice 原代码中调用其桌面文件接口的地方，应通过一层薄适配器转换为 `office.read`、`office.save` 等接口。业务逻辑尽量不直接改 vendored 代码，以便未来单独升级 DOCX 引擎。

### 9.4 许可证

- 保留 GenOffice 的 Apache-2.0 LICENSE。
- 保留第三方依赖 NOTICE 和版权文本。
- 明确排除 `ee/` 企业代码。
- `UPSTREAM.md` 记录来源仓库、提交、引入日期和本地适配说明。
- 发布包中不得遗漏第三方字体许可证。

## 10. 打开与保存流程

### 10.1 打开

1. 用户点击 DOCX。
2. 宿主解析文件关联。
3. 宿主打开 `pi.office/editor` 标签页。
4. 宿主向插件发送 `view:open` 或 `piViewOpen` 事件，带上规范化文件路径和当前会话信息。
5. 插件主进程读取文件并计算版本指纹。
6. 插件页面加载编辑器并显示内容。
7. 若编辑器不支持某类结构，页面显示只读或受限提示。

### 10.2 编辑

编辑页只修改内存中的文档模型。任何修改都会将文档标记为 dirty，并把状态同步给宿主，用于标签页提示和关闭确认。

### 10.3 保存

1. 用户按 `Ctrl+S`。
2. 插件主进程重新读取原文件指纹。
3. 若指纹与打开时不同，停止保存并要求用户处理冲突。
4. 编辑器序列化为 DOCX 字节。
5. 插件写入同目录临时文件。
6. 临时文件刷新到磁盘。
7. 原子替换原文件。
8. 返回保存结果并更新版本指纹。
9. 文档恢复为 clean 状态。

### 10.4 失败处理

| 场景 | 行为 |
| --- | --- |
| 临时文件创建失败 | 不修改原文件，提示具体错误 |
| 替换失败 | 保留原文件，清理临时文件，提示重试 |
| 序列化失败 | 不进入写入阶段，保留内存修改 |
| 冲突检测失败 | 默认阻止保存，不静默覆盖 |
| 插件进程崩溃 | 原文件保持上一次成功保存版本 |
| 应用退出 | 有未保存修改时阻止无提示退出 |
| 文件被删除 | 禁止覆盖，提示另存或取消 |

## 11. 标签页与生命周期

### 11.1 标签页规则

- 同一个规范化路径只能有一个编辑器实例。
- 不同文件可以有独立标签页。
- 再次打开同一文件时激活已有标签，不创建第二个写入者。
- 标签页标题显示文件名和 dirty 标记。
- 关闭 dirty 标签时必须经过用户确认。

### 11.2 会话切换

PI-Desktop 的工作面板上下文跟会话关联。DOCX 编辑器不能因为用户切换会话而静默丢失修改。

建议第一阶段的实现方式：

- 编辑状态以文档句柄为身份，而不是以标签视图为身份。
- 视图卸载前，插件主进程保存恢复草稿。
- 再次打开同一文件时提示“恢复未保存的编辑”。
- 若恢复机制没有完成，则切换到其他会话前必须拦截并让用户处理。

### 11.3 多窗口

第一版只支持同一应用实例内的一个编辑器实例。若以后支持多窗口，两个窗口不能同时无冲突写同一路径。

## 12. 安全边界

1. 编辑页面不能访问 Node.js、文件系统或 shell。
2. 页面只通过 `pluginBridge` 调用插件主进程的文档接口。
3. 插件主进程只处理宿主在打开流程中授权的文件路径。
4. 文件关联不授予读写权限，权限仍由插件权限和文件范围决定。
5. 第一版不启用任何网络访问。
6. 不执行 DOCX 中的宏、脚本或外部链接。
7. 不使用远程字体和远程编辑器资源。
8. 对超大文件设置明确上限或分块策略，避免内存耗尽。
9. 所有保存必须经过冲突检查和原子替换。
10. 插件错误要进入已有日志和错误提示路径，不能静默吞掉。

## 15. 验收标准

一期完成的最低标准：

- 从聊天文件引用点击 DOCX，右侧面板直接打开编辑器。
- 从文件列表点击 DOCX，使用同一个编辑器。
- 修改文字和基础样式后可以保存。
- 保存成功后关闭并重新打开，内容保持正确。
- 同一文件重复点击不会创建两个并发写入者。
- 关闭未保存文档时会询问。
- 外部程序修改文件后，保存不会静默覆盖。
- 保存失败时原文件仍可正常打开。
- 禁用 `pi.office` 后，DOCX 回退到原有查看器。
- 没有网络请求和远程资源依赖。
- Windows、macOS、Linux 上都使用同一套编辑器页面和协议。
- 插件包包含完整许可证和上游来源说明。

## 17. 实施拆解

### 工作流 A：DOCX 引擎可行性验证

目标：在接触 PI-Desktop 正式实现前，确认 GenOffice DOCX 编辑器能够完成打开、编辑、保存和再次打开的闭环。

输出：

- 一组真实 DOCX 样本。
- 引擎可编辑、可保存和不可保存的能力表。
- 复杂结构回写保真度结果。
- 是否允许进入一期的明确结论。

退出条件：

- 基础文字、列表、表格和图片样本可以往返保存。
- 不支持的结构有明确阻断策略。
- 不存在会把原文件静默写坏的已知路径。

### 工作流 B：宿主人机协议

目标：增加文件关联、打开目标视图和 dirty 状态传回。

输出：

- SDK 和清单类型。
- Rust 校验。
- 打开解析器。
- 禁用插件后的回退行为。
- ADR、规格和 E2E 文档更新。

### 工作流 C：插件骨架

目标：创建 `pi.office` 插件包、空白编辑视图和受控文件桥接。

输出：

- 插件主进程。
- 编辑页面。
- 文件读取。
- 只读预览。
- 错误和日志路径。

### 工作流 D：DOCX 编辑器接入

目标：接入 GenOffice DOCX 编辑器适配层。

输出：

- 文档加载。
- 可视编辑。
- 脏状态。
- 快捷键和基础编辑操作。
- 不支持结构的提示。

### 工作流 E：保存安全与生命周期

目标：完成原子保存、冲突处理、关闭确认和崩溃恢复策略。

输出：

- SHA-256 版本指纹。
- 临时文件和原子替换。
- 外部修改检测。
- 脏标签关闭流程。
- 会话切换恢复策略。

### 工作流 F：打包与全平台验证

目标：将插件作为内置资源打入三端安装包。

输出：

- Windows、macOS、Linux 构建。
- 字体和许可证。
- 打包完整性检查。
- 三端打开、编辑、保存、重开验证。

## 18. 验证矩阵

### 18.1 单元和集成验证

- 文件扩展名规范化。
- 文件关联优先级和重复声明校验。
- 插件禁用后的 fallback。
- 同一路径标签复用。
- 外部修改冲突检测。
- 原子保存失败不破坏原文件。
- 文件权限不可写时的错误提示。
- 文档句柄释放和进程退出清理。

### 18.2 真实文档样本

建议覆盖：

- 纯文字文档。
- 多级标题和列表。
- 表格。
- 图片。
- 中文字体。
- 页眉页脚。
- 修订记录。
- 批注。
- 脚注和尾注。
- 数学公式。
- 嵌入对象。
- 大文件。
- 损坏文件。
- 密码保护文件。

不保证编辑的样本必须进入只读或拒绝保存路径，不能仅靠警告继续写入。

### 18.3 平台验证

| 平台 | 必测内容 |
| --- | --- |
| Windows x64 | 路径、文件锁、原子替换、安装包资源 |
| macOS arm64 | 签名、公证、字体、沙箱资源 |
| macOS x64 | 资源路径和编辑器加载 |
| Linux x64 | 字体、权限、AppImage/deb/rpm 资源 |

如果第一版只发布部分平台，必须在发布说明和插件能力表中明确，不得声称全平台支持。

## 19. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| GenOffice DOCX 包为 private | 不能直接用 npm 安装 | 固定提交，vendored 源码，维护升级说明 |
| 复杂 Word 文档回写丢结构 | 用户数据损坏 | 先做保真矩阵，不支持结构阻止保存 |
| 字体不一致 | 三端分页和换行不同 | 内置字体，避免依赖系统字体 |
| 大文件通过 IPC 传输 | 面板卡顿或内存升高 | 分块读取，设置上限，懒加载编辑器 |
| 外部修改原文件 | 覆盖用户新内容 | SHA-256、mtime、size 三重检测 |
| 未保存修改跨会话丢失 | 用户数据丢失 | 文档句柄和恢复草稿，或切换前拦截 |
| 关闭标签直接销毁页面 | 修改丢失 | 宿主级 dirty 状态和关闭确认 |
| Windows 文件锁或替换失败 | 保存失败或残留临时文件 | 同目录临时文件、重试、清理和明确错误 |
| 上游升级造成适配层断裂 | 维护成本 | 固定版本，分离 vendored 与适配代码 |
| 第三方许可证遗漏 | 发布合规风险 | 许可证清单和打包检查进入验收 |

## 20. 建议的评审决策

请逐项确认：

- [ ] 同意第一版只做 DOCX，XLSX、PPTX、PDF 另行排期。
- [ ] 同意以 `pi.office` 内置插件交付，不采用外部程序或 MCP 方案。
- [ ] 同意在第一期增加通用文件关联协议，而不是在宿主里硬编码插件 ID。
- [ ] 同意复用 GenOffice 的 DOCX 编辑器和格式引擎，并固定上游提交。
- [ ] 同意不引入 GenOffice 的 Electron 壳、AI、MCP 和账户功能。
- [ ] 同意第一阶段本地运行、无网络依赖。
- [ ] 同意保存前做外部修改冲突检测，不默认覆盖。
- [ ] 同意不支持的复杂结构默认阻止保存，而不是冒险写回。
- [ ] 同意先完成 DOCX 引擎保真验证，再开始宿主和插件代码实现。
- [ ] 同意将许可证、字体和第三方 NOTICE 纳入发布验收。

6. 第一阶段的三端发布范围是否包含 Windows ARM64 和无图形界面的 Linux 环境？

## 22. 审阅通过后的下一步

1. 只执行工作流 A，完成 GenOffice DOCX 引擎的真实样本往返验证。
2. 根据验证结果确定可编辑范围和只读范围。
3. 新增 ADR，固定文件关联协议、插件边界和保存模型。

5. 在集成后的本地 `main` 上运行关联 E2E，再进入发布流程。

在 DOCX 引擎验证通过之前，不应把该功能宣称为“已完成”或“可直接发布”。
